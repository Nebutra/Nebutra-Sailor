# Database convergence — one source, generated, deployed first

- **Date:** 2026-09-25
- **Status:** Accepted
- **Owner:** Tseka Luk
- **Related:** ADR 2026-06-02 tenancy tenant-supertype model 2 (answers its Q2), ADR 2026-09-24
  Sailor convergence, ADR 2026-09-25 payment orders

## Context

Sailor is a template. A scaffold user should never run SQL by hand, and a deploy should never ship
code against a schema it does not match. Neither held.

What the database was, as found on 2026-09-25, by a live `pg_dump --schema-only` of production
diffed against the repository:

| Where | What | State |
|---|---|---|
| `schema.prisma` | 96 models | close to the tables, but missing `retention_policies` |
| `prisma/migrations/` | 42 files | **could not build a database from empty.** The first file ALTERed tables that no file created, because the pre-2026-03 tables came from `db push`. CI worked around it with `db push`. |
| migrations, "model 1" | `current_org_id()`, a `_bypass TO postgres` + `_tenant` policy per table | live |
| `infra/…/rls.sql`, "model 2" | `current_tenant_id()`, one `_rls TO app_user` policy per table, "auto-generated from FK graph" | live, generator lost, 18 tables behind |
| `infra/…/retention.sql`, `cost-guardrails.sql` | a table, a function, role settings | applied by hand |
| `provision-fresh-database.sh`, `infra/ops/scripts/setup-db.sh` | two different new-database procedures | one pointed at a path that does not exist |

Production ran **164 policies** from both models at once. Postgres ORs permissive policies, so it
worked. But no one file said what the access rule for a table was. Table ownership was split
between `postgres` (89 tables) and a PlanetScale API role (8 tables). Deploys never migrated:
`20260925010000_add_auth_device_codes` was on `main`, not in production, and `nebutra login`
failed.

## Decision

**One source, in `packages/platform/db/prisma/`. Everything else is generated from it or
re-applied from it on every deploy.**

| Artifact | Kind | Applied |
|---|---|---|
| `schema.prisma` | tables, columns, indexes, and each table's access rule as `/// @rls` | edited by people |
| `generated/rls.sql` | policies, written by a Prisma generator (`generators/rls.mjs`) on `prisma generate` | every deploy, idempotent |
| `platform.sql` | the only hand-written SQL: `purge_expired_rows()`, the runtime role's grants and session guardrails | every deploy, idempotent |
| `migrations/00000000000000_baseline` | `migrate diff --from-empty` of the schema, plus the retention seed and one CHECK | once, checksum-pinned |
| `migrations/<timestamp>_*` | generated by `prisma migrate dev`, structure only | once |

**RLS is one model.** Each table gets exactly one policy, `<table>_rls`, or the pair
`<table>_read` / `<table>_write`. There is no `TO` clause: a policy binds every role that is
neither the table owner nor BYPASSRLS, so `APP_DB_ROLE` can be any name. The `_bypass TO postgres`
policies are gone because `postgres` already has BYPASSRLS in production, which was verified.
`current_org_id()` is gone as well. A model's rule is inferred from a `tenant_id` or
`organization_id` column, or from its single tenant-scoped parent. Any other model must declare
`global | deny | off | self | tenant(col) | via(field) | using(sql) | read(sql) write(sql)`, or
generation fails. No table ships without an access decision.

**Convergence changed no behaviour.** The annotations were derived from production's effective
policies. The generated set was then applied to a copy of production and compared per table and
per command (SELECT/INSERT/UPDATE/DELETE) for the runtime role: all 384 combinations were
identical, and 164 policies became 86. Where production was permissive (24 `global` tables, 11
with RLS off), convergence kept that. Tightening them is a separate decision, listed below.

**One command, any host.** `pnpm db:deploy` (`scripts/db.mjs`) runs `prisma migrate deploy`, then
`platform.sql` + `rls.sql` in one locked transaction, then verifies. It exits non-zero on any
pending migration, any structural difference from `schema.prisma`, or any policy or RLS switch
that differs from `rls.sql`. It uses only the package's own `prisma` binary and `pg`, so it runs
the same way in a container entrypoint, a release command, a K8s init container, CI, or on a
laptop. `db:check` is the read-only half. `db:adopt` moves a database that predates the baseline
onto it once: it proves the tables already are the baseline, then swaps the history. It changes
no table. `deploy` refuses a legacy, pushed or half-failed database with the exact next step.

**Deploys migrate first.** `ops-database-migrate.yml` is now a reusable workflow
(`deploy | check | adopt`). `deploy-fly`, `deploy-ai-origin-fly` and `deploy-fly-gateway` call it
as their first job, and every app job `needs` it, so a drifted database stops the deploy.

**Guarded.** `scripts/lint-database.mjs` runs in `pnpm lint`. It checks that the baseline
checksum is pinned in `governance.config.json`, and that migrations are structure-only: no
policy, RLS switch, function, grant or role. Destructive statements need
`-- nebutra:destructive <reason>`. Migration folders are Prisma-shaped. No `CREATE POLICY` may
appear anywhere else. CI's Database Schema Check builds the database from empty twice with
`db:deploy` and fails on a stale `rls.sql`. The rules for people and agents are at the top of
`packages/platform/db/README.md`, with pointers in `CLAUDE.md` and `AGENTS.md`.

## Consequences

- An empty database builds with one command, for the first time. `provision-fresh-database.sh`
  is reduced to the one thing a deploy cannot do (create the login role, which needs a
  password), followed by `db:deploy` and its isolation self-check.
- Retired: `infra/data/database/policies/{rls,retention,cost-guardrails}.sql`,
  `infra/ops/scripts/setup-db.sh`, `scripts/verify-migrations.mts`, the four per-migration tests,
  and the `db push` path of the migration workflow. `rls-migration-coverage.test.ts` keeps all
  260 cross-tenant assertions and now reads the generated file.
- Production cutover, in order, rehearsed end to end on a restored copy:
  1. apply the last legacy migration (`add_auth_device_codes`) through the old workflow on `main`;
  2. run `ops-database-migrate` with `action=adopt` from this branch. It records the baseline and
     re-applies RLS, and no table changes;
  3. merge. From then on, every deploy runs `db:deploy` first.
- Branches that add migrations under the old layout (for example payment orders) regenerate them
  as a delta after the baseline, and drop any hand-written policy for an `/// @rls` rule.
- Not decided here, and flagged for a separate review: whether the 24 `global` and 11 `off`
  tables (for example `auth_sessions`, `users`, `desktop_auth_*`) should be tightened, and
  whether table ownership should be unified under one role.
