# Payment orders — one money path, whatever is being sold

- **Date:** 2026-09-25
- **Status:** Accepted
- **Owner:** Tseka Luk
- **Related:** ADR 2026-09-24 Sailor convergence (payments stay Stripe + WeChat Pay/Alipay)

## Context

The business model is not decided yet: credits, a subscription, a lifetime licence and API quota are
all still possible. The payment code had already decided for it. The only purchase path was
"buy credits", and three things about it would have been wrong under any model:

1. **The client set the price.** `POST /billing/credits/checkout` took `creditAmount` and `amount`
   from the request body and charged exactly that, so 250,000 credits could be bought for ¥0.01.
2. **Nothing recorded the money.** A wallet notification credited the organization straight from
   the `attach` metadata it carried. There was no row to reconcile a lost notification against,
   check the paid amount with, or refund from.
3. **What was sold was the payment path.** Selling anything but credits meant a new checkout route,
   a new webhook branch and a new metadata format.

## Decision

Split a purchase into three parts that change for different reasons:

| Part | What it is | Changes when |
|---|---|---|
| **Offer** (`@nebutra/billing` `offers/`) | Data: id, name, price per currency, and a fulfillment spec `{ type, params }` | the business model or pricing changes. Edit the catalog, not code |
| **PaymentOrder** (`payment_orders` table) | One attempt to pay for one offer. The price and a snapshot of the fulfillment spec are locked at checkout | never, per order |
| **Fulfillment** (`fulfillment/`) | A handler per `type` with `fulfill` and an optional `revoke`. `credits` is built in | a new kind of product is sold. Register a handler |

The flow:

- **create:** the request names `offerId` + `method`. The server prices the offer in the
  method's currency (card → USD via Stripe, alipay/wechat → CNY), writes the order, then opens the
  provider session. The order id *is* the wallet's `out_trade_no`, so no metadata travels with the
  payment.
- **settle:** a webhook (or reconcile) reports the order paid. The paid amount must equal the
  locked `amountMinor` in the locked currency, or the order is refused and never fulfilled. Moving
  to `PAID` is a conditional update, so racing reports settle it once.
- **fulfill:** runs the handler, then sets `fulfilledAt`. Handlers are idempotent on the order id
  (credits use it as the ledger's `relatedId`).
- **reconcile:** an Inngest cron runs every 2 minutes. It asks the wallet about orders still pending
  2 minutes after creation, expires orders past their 30-minute window, and retries fulfillment
  for orders paid but not handed over. Stripe orders rely on Stripe's own webhook retries.
- **refund:** `POST /api/v1/admin/payment-orders/{id}/refund`. Money first (idempotent on
  `refundId` at the provider), then a guarded row update, then `revoke` with the refunded share.
  `revoked: false` means the money went back but the grant could not (for example, the credits
  were already spent). That goes to a person to decide. The code does not absorb it silently.

Amounts are integer minor units (cents, fen) everywhere past the catalog.

## Consequences

- Changing the business model means editing the offer catalog (`configureOffers()` at boot) and,
  for a new kind of product, registering one fulfillment handler. Checkout, webhooks, reconcile and
  refunds do not change.
- `POST /billing/credits/checkout` and `GET /billing/credits/pricing` are removed. Their
  replacements are `POST /billing/orders` and `GET /billing/offers`. No web surface called the old
  pair.
- Stripe checkout sessions opened before this change still complete through the legacy
  `credit_purchase` metadata branch. Wallet payments were never live, so they have no legacy path.
- The migration `20260926100000_payment_orders` was generated by Prisma from `schema.prisma` and is
  additive: an enum and a table. RLS is inferred from `tenant_id` (ADR 2026-09-25 database
  convergence), so there is no hand-written policy. It ships with the first deploy after merge,
  because every deploy runs `db:deploy` first.
- **Not yet done:** a purchase UI, and more `successUrl` origins for the mainland entry
  (`cn.nebutra.com`). `assertProductReturnUrl` allows only the product origin today.
