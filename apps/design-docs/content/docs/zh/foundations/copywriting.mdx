---
title: 文案规范
description: 产品与营销表面的语气、表达和 UI 文案约定。
---

## 概览
文案规范覆盖用户会读到的每一个词：按钮标签、错误消息、空状态、Tooltip、引导提示和营销标题。一致的 UI 文案能降低认知负担，并建立信任。

两类表面使用不同的表达语域：

| 表面 | 语域 | 优先级 |
|---|---|---|
| 产品 UI | 简洁、功能性、冷静 | 清晰度与任务完成 |
| 营销 | 有吸引力、具体、自信 | 转化与可信度 |

这些规范同时适用于两者。原则一致，但语气随上下文调整。

## 设计依据

用户不会逐字阅读 UI，而是扫描。每多一个词，都会竞争注意力。好的 UI 文案应该近乎隐形：它确认用户已有预期，并在流程顺利时尽量不打扰。

当事情出错时，文案会变成屏幕上最重要的设计元素。清晰的错误消息能帮助用户恢复，不清晰的错误消息会让用户流失。

## 表达原则

Nebutra 的表达原则是：

- **直接**：说清楚你的意思。避免模糊措辞（`try to`、`you might want to`、`in some cases`）。
- **具体**：用具体信息替代模糊限定词。
- **像人说话**：写给真实用户，而不是合规清单。除非用户是技术受众且术语足够精确，否则避免行话。
- **自信但不傲慢**：不要过度解释，也不要无意义道歉。

Nebutra 的声音不应该是：
- 轻佻到显得不专业
- 过度正式或法律化
- 空洞热情（`Awesome!`、`Amazing!`、`Great job!`）

## 按场景区分语气

### 错误与失败状态

语气：中性、直接、聚焦恢复。

说明发生了什么、为什么发生（如果可知），以及下一步怎么做。不要责怪用户。

| 错误 | 正确 |
|---|---|
| "Something went wrong." | "Your payment could not be processed. Check your card details and try again." |
| "Invalid input." | "Email address must include @." |
| "Error 422." | "We could not save your changes. Your session may have expired — sign in again." |

### 空状态

语气：有帮助、以行动为导向。

空状态是引导用户完成第一步的机会。不要只描述“没有内容”，要告诉用户下一步可以做什么。

| 错误 | 正确 |
|---|---|
| "No projects found." | "Create your first project to get started." |
| "Nothing here yet." | "Invite teammates to collaborate on this workspace." |

### 确认与成功

语气：简短、确认完成，然后退场。

```
File deleted.       ← 正确（过去时，2 个词）
Your file has been successfully deleted!  ← 错误（冗长、空洞）
```

### 破坏性操作

语气：冷静、精确，把不可逆后果作为事实说明，不制造恐慌。

把后果说清楚，但不要制造恐慌。

```
Delete project?
This cannot be undone. All tasks, files, and history will be permanently removed.

[Cancel]  [Delete project]
```

### 按钮与 CTA

- 使用“动词 + 名词”结构：**Create project**、**Delete account**、**Invite member**
- 按钮文案要匹配对话框标题或被确认的具体动作
- 避免通用标签：**OK**、**Submit**、**Confirm**。这些词会迫使用户重新阅读上下文

| 错误 | 正确 |
|---|---|
| Submit | Save changes |
| OK | Got it |
| Confirm | Delete project |
| Yes | Remove member |

### 加载与进度

- 使用进行时：**Uploading…**、**Saving…**、**Processing payment…**
- 如果等待较久，给出具体原因：**Analyzing 3,400 records…**
- 不要默认使用 **Loading…**，要具体说明正在加载什么

## 使用准则
### 大小写

- 所有 UI 文案使用 **Sentence case**：标题、按钮、Tooltip、消息都一致
- **Title Case** 只用于产品名、功能名和专有名词
- **ALL CAPS** 只用于 overline 标签和徽标，不用于正文

```
错误：Save Changes   ← 按钮不应使用 Title Case
正确：Save changes

错误：this is a section heading
正确：This is a section heading
```

### 标点

- 按钮标签、标题、Tooltip 末尾不加句号
- 错误消息和说明性正文使用句号
- 插入说明使用 em dash（—），不要使用双连字符（--）
- 正文避免省略号；只在截断文本或进行中状态中使用

### 数字与单位

- 英文文案中 one 到 nine 拼写出来，10 及以上使用数字
- 使用缩写单位：2 MB、14 days、3 users，缩写中不加句点
- 大数字使用逗号分组：1,200 records

### 时间与日期

- 近期事件使用相对时间：3 minutes ago、Yesterday
- 超过 7 天的事件使用绝对日期：Feb 14, 2026
- 技术场景使用 24 小时制；通用受众使用带 AM/PM 的 12 小时制

## 营销文案

营销文案遵循同一套声音，但允许更高能量。

**标题：**
- 先讲结果，不先讲功能
- 有证据时使用具体数字："Deploy in 30 seconds"、"99.99% uptime"
- 避免无证据最高级："the best"、"world-class"、"unmatched"

**副标题与正文：**
- 用具体、可信的论断支撑标题
- 每段只表达一个想法
- 以清晰 CTA 结束

**CTA：**
- 第一人称框架通常转化更好：**Start my free trial** 优于 **Start free trial**
- 具体性降低阻力：**See pricing** 优于 **Learn more**

## 应做 / 禁止

**应做**所有 UI 文案、标题和按钮标签都使用 sentence case。

**应做**错误消息同时说明原因和恢复动作。

**应做**按钮标签匹配正在执行的精确动作，尤其是破坏性确认对话框。

**应做**营销文案使用具体语言，并用数字支撑主张。

**禁止**使用填充短语："Please note that…"、"It looks like…"、"We noticed that…"

**禁止**过度道歉。错误消息中一次真诚道歉可以接受，但 `We're sorry. We're sorry this happened. We apologize for the inconvenience.` 不可接受。

**禁止**在错误或说明中使用被动语态。"Your payment was declined" → "We could not process your payment."

**禁止**在错误状态或警告中使用感叹号。只在真正值得庆祝的时刻使用，例如完成 onboarding 或达成第一个里程碑。
