docs 信息架构只优化一个问题：**产品工程师在创建 UI 之前应该先复用什么？**

答案必须分层。Token 页面不能写成组件页面，primitive 页面不能变成营销画廊，registry manifest 也不能伪装成设计真相源。

## 层级

| 层级 | 负责 | 不负责 |
| --- | --- | --- |
| 系统基础 | 品牌源数据、运行时 token 语义、排版、动效、可访问性、文案规则 | 组件专属 API 决策 |
| 组件系统 | `@nebutra/ui` 中可复用的 primitives 和受治理产品表面 | 一次性功能 UI |
| 产品组合 | 由 primitives 组装出的重复页面区块 | 新视觉语言 |
| 运行模式 | 表单、表格、导航、弹层、空状态等跨组件工作流 | 具体组件 props |
| API 契约 | 会影响 UI 状态的 system、legal、event 契约 | 视觉表现 |
| Registry | 面向外部消费者的 shadcn-compatible 安装清单 | 设计系统权威 |

## 导航模型

侧边栏按消费者意图组织，而不是按组件诞生时间排序：

1. **系统基础**：先理解 tokens、品牌约束、动效和可访问性，再触碰组件。
2. **组件系统**：按任务选择 primitive：表单、导航、弹层、反馈、数据、布局、AI、动效、视觉系统、内容区块、媒体。
3. **产品组合**：当页面形态已经存在时，直接复用组装好的 SaaS 区块。
4. **运行模式**：让跨组件工作流保持一致。
5. **API 契约**：把会驱动 loading、error、empty、legal、event 状态的非视觉契约放在文档内。

## 组件页面契约

成熟组件页必须回答相同的问题：

| 模块 | 必须回答 |
| --- | --- |
| Demo | 渲染是否等价于生产组件，并覆盖 light/dark 行为？ |
| Usage | 消费者应该使用哪个 import path 和最低接入步骤？ |
| Anatomy | 哪些子部件是公开 API，哪些内部结构不能被选择器穿透？ |
| Variants | 哪些变体组合是设计意图，且由 token 支撑？ |
| State machine | empty、loading、disabled、error、selected、async 状态如何表现？ |
| Accessibility | 保证了什么语义元素、ARIA 契约、焦点行为和键盘路径？ |
| Registry | 是否可以作为独立 manifest 安装，还是只能通过 package 使用？ |

## Frontmatter 契约

schema 已支持治理元数据，即使旧页面尚未全部补齐：

```yaml
status: stable | beta | deprecated | experimental
layer: foundation | primitive | composition | pattern | registry | api | guide
owner: Design Systems
package: "@nebutra/ui"
source: packages/design/ui/src/primitives/button.tsx
primitive: Button
substrate: base-ui | native | custom | lobe-ui | radix | cmdk | vaul | mixed
registry: true
storybook: packages/design/ui/src/primitives/button.stories.tsx
tokens:
  - --button-bg-primary
a11y:
  - keyboard
  - focus-visible
lastVerified: "2026-05-21"
```

补齐这些字段不是文档洁癖。它能让工具发现组件页还在写 “Radix”，但源码已经迁到 Base UI；也能发现 registry item 已经发布，却没有对应契约页。

## Registry 策略

monorepo 内部以 npm package import 为准：

```tsx
import { Button } from "@nebutra/ui/primitives";
```

公开 registry 是外部分发渠道：

```bash
npx shadcn@latest add https://ui.nebutra.com/r/button.json
```

这个区别很重要。Registry JSON 可以携带复制出来的源码和独立 token fallback，但它不定义产品语义。真正定义契约的是 MDX 页面、Storybook story、package source 和 component tokens。

## 漂移门禁

docs、registry、previews 或组件导航变化时运行：

```bash
pnpm --filter @nebutra/design-docs lint:ia
```

它会检查：

- sidebar meta 是否列出所有已提交页面，并且没有不存在的页面；
- 英文和中文 section 是否结构配对；
- 每个 `ComponentPreview` 是否映射到生成的 preview entry；
- registry index item 是否有文档或显式 allowlist；
- 组件源码已迁移后，文档里不能残留 “built on Radix” 这类旧底层叙述；
- `#6366f1`、`#3B82F6` 这类漂移品牌色不能重新进入 docs。
