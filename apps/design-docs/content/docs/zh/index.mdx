Nebutra Design System 是 Nebutra 产品的生产级 UI 契约。它不是灵感板，也不是 demo 陈列柜：每一页都应该说明由哪一层负责设计决策、消费者应该从哪里导入、哪些 token 才是可信来源，以及新建组件之前应该优先复用什么。

## 工作模型

| 层级 | 真相源 | 消费者决策 |
| --- | --- | --- |
| 品牌数据 | `@nebutra/brand` | 用于 VI、品牌叙事和源数据。运行时 UI 不直接导入。 |
| 运行时 tokens | `@nebutra/tokens/styles.css` | 每个应用只引入一次。组件消费 semantic/component CSS 变量。 |
| 原语 | `@nebutra/ui/primitives` 或 `@nebutra/ui/primitives/canonical` | 构建产品界面时优先使用。先通过 variants 扩展，再考虑新建同类组件。 |
| 组合 | `fragment-components` 与产品 patterns | 用于重复出现的 SaaS 页面区块，不承载一次性的营销装饰。 |
| Registry | `https://ui.nebutra.com/r/<name>.json` | 面向外部消费者的 copy-paste 分发。monorepo 内部仍以 npm package 为准。 |

## 不可妥协项

1. 组件文档必须描述当前真实底层。Radix、Base UI、原生 HTML、自研 primitive 不是可以混用的标签。
2. 示例必须走公开 API 和 semantic/component tokens。穿透内部子节点选择器的 demo 是文档债务。
3. 英文和中文文档保持结构配对。一个 locale 公开的页面，另一个 locale 也要有对应页，除非有明确治理例外。
4. Registry 是分发产物，不是设计权威。MDX 文档和 package source 才定义组件契约。
