Changing the design system is a governance act. A contribution is accepted when it improves UX, keeps downstream DX legible, and reduces total system debt.

## Before You Add Anything

<Warning>
  Do not create a new component because a pasted design looks different. First prove the existing primitive, variant, or composition cannot express the semantic job.
</Warning>

Use this decision order:

1. **Reuse** an existing primitive or composition.
2. **Extend** an existing API with a variant, slot, or token when the semantic job belongs there.
3. **Promote** a repeated local pattern into the system when it appears across product surfaces.
4. **Create** a new primitive only when no existing surface can own the behavior without corrupting its API.

## Required Evidence

| Evidence | What it proves |
| --- | --- |
| Source path | The component or pattern exists in product code or the package source. |
| Token mapping | Styling consumes semantic/component tokens, not raw palette drift. |
| API decision | Names, variants, and controlled/uncontrolled state are typed clearly. |
| Storybook coverage | Default, variants, edge cases, accessibility, and dark mode render. |
| MDX docs | Usage, anatomy, state machine, props, and accessibility are documented. |
| Registry decision | Standalone install is either generated or explicitly out of scope. |

## Page Requirements

Every component page should include:

- `ComponentPreview` that renders the real component or a faithful demo;
- installation/import section with canonical package path;
- usage example that does not depend on hidden MDX globals;
- anatomy or API ownership notes for compound components;
- variant and state coverage, including empty/loading/error/disabled where relevant;
- accessibility contract with semantic element, keyboard behavior, focus behavior, and ARIA links;
- registry command when the component is in `public/registry.json` or `public/r`.

## Frontmatter

Add governance metadata as the component matures:

```yaml
status: stable
layer: primitive
owner: Design Systems
package: "@nebutra/ui"
source: packages/design/ui/src/primitives/button.tsx
primitive: Button
substrate: native
registry: true
storybook: packages/design/ui/src/primitives/button.stories.tsx
tokens:
  - --button-bg-primary
a11y:
  - keyboard
  - focus-visible
lastVerified: "2026-05-21"
```

## Prohibited

- Raw brand or palette values in component docs unless the page is explicitly explaining the token source.
- `transition: all` or hard-coded animation timing when motion tokens exist.
- Styling through internal child selectors in public examples.
- Saying a primitive is built on Radix/Base UI/native HTML when the source says otherwise.
- Updating only Storybook or only MDX when the component API changed.
- Keeping a rotten API solely to avoid migration work. Compatibility can be staged; semantic drift should not be preserved.

## Validation

Run the focused docs checks before shipping:

```bash
pnpm --filter @nebutra/design-docs lint:ia
pnpm --filter @nebutra/design-docs lint:links
pnpm --filter @nebutra/design-docs typecheck
pnpm --filter @nebutra/design-docs build
```

If a global repo check fails from unrelated packages, name the blocker and still provide focused proof for the touched docs, registry, and component surfaces.
