## Accessibility

- Use a native `<button>` for mutations such as saving billing settings, rotating an API key, or inviting a member.
- Use `ButtonLink` or `asChild` only when the action is navigation, for example opening audit log detail or moving to plan checkout.
- Loading buttons keep their accessible name through `children`; pair long-running mutations with `aria-busy` on the surrounding form region when the page state also changes.
- Icon-only buttons must provide `aria-label`, such as `Copy webhook URL` or `Refresh deployment status`.
- Keyboard focus must use the tokenized ring and remain visible on default, outline, secondary, ghost, destructive, and warning variants.

## Design Contract

- Use one primary action per decision area: Save Project, Create API Key, Invite Member, Upgrade Plan.
- Keep destructive actions visually isolated from routine submits. Use `destructive` for irreversible tenant, token, webhook, or billing changes; use `warning` for risky but recoverable actions such as pausing automation.
- Prefer `prefix` and `suffix` for icons so spacing, line height, disabled opacity, and loading replacement stay governed by the primitive.
- Keep `disabled` for impossible actions, such as a missing required field. Use `loading` for in-flight actions so the button size and label remain stable.
- Do not widen buttons with one-off classes inside dense SaaS toolbars. Use `size="tiny"` or `size="sm"` for table rows and command surfaces; use `default` or `lg` for form footers and onboarding steps.

### State Matrix

| State | Product use | Contract |
|---|---|---|
| Default | Ready submit, open dialog, copy command | Visible label names the action, not the destination object alone. |
| Hover | Pointer confirmation in toolbars and cards | Color shift stays tokenized; no layout movement. |
| Focus | Keyboard path through billing, IAM, and audit tools | Ring is visible on every variant and never clipped by parent overflow. |
| Loading | Saving tenant settings, generating API key, deploying template | Keep the final label in place; avoid changing to vague text like `Working`. |
| Disabled | Required input missing, permission denied, plan unavailable | Pair disabled controls with nearby explanatory text when the reason is not obvious. |
| Destructive | Delete organization, revoke token, purge webhook endpoint | Confirm in a dialog or secondary step before executing. |

## Real Product Examples

- `Save Billing Details` as the only primary action in an invoice profile form, with secondary `Cancel` as `outline`.
- `Invite Member` in the organization settings toolbar, using a prefix icon and preserving the label while the invite request is loading.
- `Rotate API Key` as `warning` until the confirmation dialog, then `destructive` for the final irreversible revoke action.
- Icon-only `Copy webhook signing secret` in an integration row, with `aria-label` and a tooltip that mirrors the label.

## Anti-patterns

- Do not use `link` variant for destructive or form-submitting actions.
- Do not place two visually primary buttons in the same action group.
- Do not hide a loading mutation by disabling the button without progress feedback.
- Do not use custom padding or raw colors to make a local "special" button for one product page.
- Do not put tooltip-only text on icon buttons; the accessible label must exist without hover.
