## Overview

> This page previously documented a `createTheme()` / `DesignSystemProvider` / `generateMarketingCSSVars()`
> API attributed to `apps/docs-hub`. None of that exists in the repo — `apps/docs-hub` was never a
> real app, and none of those exports exist anywhere in `@nebutra/ui`. This page now documents the
> theming mechanism that actually ships.

Theming is split across three packages, each with a distinct job:

| Layer | Package | Role |
|---|---|---|
| Runtime tokens (SSOT) | `@nebutra/tokens` | `styles.css` (CSS variables) + `ThemeProvider`/`useTheme` (light/dark mode) |
| Language swap | `@nebutra/theme` | Brand Packages + `applyLanguage()` + `skins.css`, scoped to `html[data-brand]` |
| Component bridge | `@nebutra/ui` | `NebutraThemeProvider` — wraps Lobe UI with the same tokens |

## Runtime tokens — `@nebutra/tokens`

`@nebutra/tokens` is the single source of truth for runtime design tokens. Import the generated
stylesheet once, at the app root:

```css
@import "@nebutra/tokens/styles.css";
@import "@nebutra/tokens/recipe.css";
```

`styles.css` declares:

- Brand color scales (`--nebutra-blue-*`, `--nebutra-cyan-*`)
- 12-step functional scales (`--neutral-1..12`, `--blue-1..12`, `--cyan-1..12`)
- Semantic variables (`--primary`, `--background`, `--border`, etc.) as **bare HSL channel triples**
  — wrap them (`hsl(var(--border))`) when they land in a color slot, or use the semantic Tailwind
  utility instead. See [Nebutra Tokens](/en/docs/foundations/nebutra-tokens) for why.
- Light/dark mode via `:root` / `.dark`
- Display-P3 wide gamut with sRGB fallback
- Tailwind v4 `@theme` integration

`styles.css` itself is **generated** — see [Nebutra Tokens](/en/docs/foundations/nebutra-tokens) for
the editable source.

### `ThemeProvider` / `useTheme` — light/dark mode

```tsx
import { ThemeProvider, useTheme } from "@nebutra/tokens";

// App root
<ThemeProvider attribute="class" defaultTheme="system" enableSystem>
  <App />
</ThemeProvider>;

// Anywhere inside the tree
function ThemeToggle() {
  const { resolvedTheme, setTheme } = useTheme();
  return (
    <button type="button" onClick={() => setTheme(resolvedTheme === "light" ? "dark" : "light")}>
      Current: {resolvedTheme}
    </button>
  );
}
```

This is a hand-rolled replacement for `next-themes` (same prop and hook names, drop-in migration),
not a re-export of it — `next-themes@0.4.x` renders an inline `<script>` inside a Client Component,
which React 19 + Next.js 16 (Turbopack) now flags. The provider splits into a client `ThemeProvider`
(runtime state, OS sync) and writes a cookie so Server Components can read the resolved theme via
`next/headers` `cookies()` and inject the class directly into `<html>` — no inline script, no FOUC.

**`ThemeProviderProps`:**

| Prop | Type | Default | Description |
|---|---|---|---|
| `attribute` | `"class" \| "data-theme"` | `"class"` | DOM attribute set on `<html>` |
| `defaultTheme` | `"light" \| "dark" \| "system"` | `"system"` | Initial preference |
| `enableSystem` | `boolean` | `true` | Follow OS preference when `theme === "system"` |
| `storageKey` | `string` | `"theme"` | localStorage / cookie key |
| `children` | `ReactNode` | — | Application subtree |

**`useTheme()` return value:**

| Property | Type | Description |
|---|---|---|
| `theme` | `"light" \| "dark" \| "system"` | The raw user preference |
| `resolvedTheme` | `"light" \| "dark"` | The concretely-applied theme |
| `systemTheme` | `"light" \| "dark"` | The OS-level preference |
| `setTheme` | `(theme) => void` | Imperatively switch the preference |

Wrap the app root with `ThemeProvider` exactly once. Read and toggle mode through `useTheme()` —
don't manage theme state independently.

## Language swap — `@nebutra/theme`

`@nebutra/theme` is a separate, optional layer: global product-chrome swap (e.g. a Create Center /
multi-tenant SaaS letting a tenant pick a whole design language). It is **not** light/dark mode —
that's `@nebutra/tokens` above.

> **Removed (2026-07):** 78 oklch "mood" presets under `[data-theme]` (`neon`, `gradient`,
> `dark-dense`, `minimal`, `vibrant`, `ocean`). They dual-wrote product chrome and fought the carrier
> model. Do not reintroduce them.

```css
@import "@nebutra/theme/skins.css"; /* multi-language, scoped to html[data-brand] */
```

```ts
import { applyLanguage, clearLanguage, LANGUAGE_REGISTRY } from "@nebutra/theme";

applyLanguage("vanta", { persist: true }); // built-in Brand Package
clearLanguage(); // back to factory tokens
```

Built-in catalog (`id` → what it proves): `factory` (default SSOT), `linear`, `gsap`, `raycast`,
`vercel`, `vanta`, `stripe`, `notion`. Inspect with the CLI:

```bash
nebutra theme list
nebutra theme inspect vanta
```

## Component bridge — `@nebutra/ui`

`@nebutra/ui` ships some components (Lobe UI / Ant Design derived) that need their own theme
context. `NebutraThemeProvider` wraps that context with the same brand tokens — it does not replace
`ThemeProvider` from `@nebutra/tokens`.

```tsx
import { NebutraThemeProvider } from "@nebutra/ui";

<NebutraThemeProvider appearance="auto" defaultAppearance="light">
  <App />
</NebutraThemeProvider>;
```

**`NebutraThemeProviderProps`:**

| Prop | Type | Default | Description |
|---|---|---|---|
| `appearance` | `"dark" \| "light" \| "auto"` | `"auto"` | Force a mode, or follow `defaultAppearance` |
| `defaultAppearance` | `"dark" \| "light"` | `"light"` | Fallback when `appearance === "auto"` |
| `children` | `ReactNode` | — | Subtree |

## Do / Don't

**Do** import `@nebutra/tokens/styles.css` once, at the app root, before any component styles.

**Do** use `useTheme()` from `@nebutra/tokens` to read and toggle light/dark mode.

**Do** wrap bare-HSL-channel semantic tokens (`--background`, `--border`, …) in `hsl(...)` whenever
they land in a color slot — an unwrapped `var(--border)` there invalidates the whole declaration and
the browser silently discards it.

**Don't** hand-edit `packages/design/tokens/styles.css` — it's generated. Edit the DTCG source under
`packages/design/design-tokens/tokens/` instead.

**Don't** reach for `@nebutra/theme`'s `applyLanguage()` for ordinary light/dark mode — that's a
whole-product-chrome swap, not a mode toggle.

**Don't** nest multiple `ThemeProvider` instances. A single provider at the root governs the entire
tree.
