The docs architecture is optimized for one question: **what should a product engineer reuse before creating UI?**

The answer is intentionally layered. A token page should not read like a component page, a primitive page should not behave like a marketing gallery, and registry manifests should not pretend to be the source of design truth.

## Layers

| Layer | Owns | Does not own |
| --- | --- | --- |
| Foundations | Brand source data, runtime token semantics, typography, motion, accessibility, copy rules | Component-specific API decisions |
| Component System | Reusable primitives and governed product surfaces from `@nebutra/ui` | One-off feature UI |
| Product Compositions | Repeated page sections assembled from primitives | New visual language |
| Operating Patterns | Cross-component workflow rules such as forms, tables, navigation, modality, and empty states | Concrete component props |
| API Contracts | System, legal, and event contracts that affect UI states | Visual treatment |
| Registry | External shadcn-compatible installation manifests | Design-system authority |

## Navigation Model

The sidebar is organized by consumer intent, not by implementation chronology:

1. **System Foundations**: learn tokens, brand constraints, motion and accessibility before touching components.
2. **Component System**: pick the primitive by job-to-be-done: forms, navigation, overlays, feedback, data, layout, AI, motion, visual systems, content blocks, media.
3. **Product Compositions**: reuse assembled SaaS sections when the page shape already exists.
4. **Operating Patterns**: align interaction workflows across component families.
5. **API Contracts**: keep non-visual contracts visible because they drive loading, error, empty, legal, and event states.

## Component Page Contract

Every mature component page should answer the same questions:

| Section | Required answer |
| --- | --- |
| Demo | Does the rendered surface match the production component and expose light/dark behavior? |
| Usage | Which import path and minimum setup should consumers use? |
| Anatomy | Which subparts are public API, and which internal structure must not be targeted? |
| Variants | Which variant combinations are intentional and token-backed? |
| State machine | What are the empty, loading, disabled, error, selected, and async states? |
| Accessibility | Which semantic element, ARIA contract, focus behavior, and keyboard path are guaranteed? |
| Registry | Is this installable as a standalone manifest, or package-only? |

## Frontmatter Contract

The schema supports governance metadata even when older pages have not been fully backfilled:

```yaml
status: stable | beta | deprecated | experimental
layer: foundation | primitive | composition | pattern | registry | api | guide
owner: Design Systems
package: "@nebutra/ui"
source: packages/design/ui/src/primitives/button.tsx
primitive: Button
substrate: base-ui | native | custom | lobe-ui | radix | cmdk | vaul | mixed
registry: true
storybook: packages/design/ui/src/primitives/button.stories.tsx
tokens:
  - --button-bg-primary
a11y:
  - keyboard
  - focus-visible
lastVerified: "2026-05-21"
```

Backfilling this metadata is not busywork. It lets docs tooling detect when a component page says "Radix" while the source has moved to Base UI, or when a registry item ships without a documented page.

## Registry Policy

Inside the monorepo, npm package imports are canonical:

```tsx
import { Button } from "@nebutra/ui/primitives";
```

The public registry is a distribution channel for external consumers:

```bash
npx shadcn@latest add https://ui.nebutra.com/r/button.json
```

That distinction matters. Registry JSON can carry copied source and standalone token fallbacks, but it does not define product semantics. The MDX page, Storybook story, package source, and component tokens define the contract.

## Drift Guard

Run the IA guard whenever docs, registry, previews, or component navigation changes:

```bash
pnpm --filter @nebutra/design-docs lint:ia
```

It checks:

- sidebar meta files list every checked-in page and no missing page;
- English and Chinese sections stay structurally paired;
- every `ComponentPreview` maps to a generated preview entry;
- every registry index item has an English docs page;
- registry and Storybook coverage exceptions are not a normal flow. If an exception is reintroduced, it must be structured debt with an owner, reason, and expiry;
- stale substrate language such as "built on Radix" is removed when the primitive source has moved on;
- drifted brand literals such as `#0033FE` and `#0033FE` do not re-enter docs.
