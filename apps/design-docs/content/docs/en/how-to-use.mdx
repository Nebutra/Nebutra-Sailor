## Choose the Consumption Path

| Context | Use | Why |
| --- | --- | --- |
| Nebutra monorepo app | npm workspace package imports | Keeps source, types, stories, and docs aligned. |
| External Next.js/React app | shadcn-compatible registry | Copies standalone source into the host project. |
| Brand/VI work | `@nebutra/brand` source data | Keeps identity data separate from runtime UI styling. |

## Monorepo Setup

<Steps>
  <Step title="Install package dependencies">
    Add the package you consume from the repo root:

    ```bash
    pnpm add @nebutra/ui @nebutra/tokens @nebutra/icons --filter <app-name>
    ```
  </Step>

  <Step title="Import runtime token CSS once">
    Add the token stylesheet in the app-level CSS entry:

    ```css
    @import "@nebutra/tokens/styles.css";
    ```
  </Step>

  <Step title="Wire theme state at the app root">
    Use `ThemeProvider` from `@nebutra/tokens`. It writes the resolved theme to the DOM and stores the preference for SSR-safe rendering.

    ```tsx
    "use client";

    import { ThemeProvider } from "@nebutra/tokens";

    export function Providers({ children }: { children: React.ReactNode }) {
      return (
        <ThemeProvider attribute="class" defaultTheme="system" enableSystem>
          {children}
        </ThemeProvider>
      );
    }
    ```
  </Step>

  <Step title="Import from the narrowest stable path">
    Prefer explicit public subpaths. Use `@nebutra/ui/primitives/canonical` when you intentionally want only governed core primitives.

    ```tsx
    import { Button, Input, Select } from "@nebutra/ui/primitives";
    import { PageHeader } from "@nebutra/ui/layout";
    import { Search } from "@nebutra/icons";
    import { cn } from "@nebutra/ui/utils";
    ```
  </Step>
</Steps>

## Registry Setup

Use registry installation only when copying a standalone component into an external project:

```bash
npx shadcn@latest add https://ui.nebutra.com/r/button.json
```

Registry manifests are shadcn-compatible distribution artifacts. They may include copied source and token fallbacks, but the package source and MDX docs remain the authority for semantics.

## Import Path Policy

| Import | Use for | Avoid when |
| --- | --- | --- |
| `@nebutra/ui/primitives` | Governed UI primitives and product surfaces | You need only the canonical core subset. |
| `@nebutra/ui/primitives/canonical` | Stable primitives for app teams that want a smaller decision surface | You need experimental or decorative surfaces. |
| `@nebutra/ui/layout` | Page shells and repeated layout helpers | You are composing a low-level primitive. |
| `@nebutra/ui/patterns` | Docs/product patterns that are intentionally higher-level | You are writing a reusable primitive. |
| `@nebutra/tokens` | ThemeProvider and runtime token state | You only need a CSS variable in component code. |
| `@nebutra/tokens/styles.css` | Runtime CSS variables | Never import inside a component file. |

## Styling Rules

```tsx
// Good: semantic/component tokens through the component API.
<Button intent="primary">Deploy</Button>

// Good: CSS variables when composing local layout.
<div className="border-[var(--border)] bg-[var(--background)] text-[var(--foreground)]" />

// Bad: raw palette drift in product UI.
<div className="bg-blue-600 text-white" />

// Bad: piercing component internals from docs or app code.
<Progress className="[&>div]:bg-green-500" />
```

If a component cannot express a needed state without internal selectors or raw palette classes, promote the missing semantic/component token or variant. Do not normalize the workaround in docs.
