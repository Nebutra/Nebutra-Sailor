Nebutra Design System is the production UI contract for Nebutra products. It is not a moodboard and it is not a demo shelf: every page should tell a consumer which layer owns the decision, which API to import, which token family to trust, and which pattern to reuse before creating something new.

## Working Model

| Layer | Source of truth | Consumer decision |
| --- | --- | --- |
| Brand data | `@nebutra/brand` | Use for VI, brand narrative, and source data. Runtime UI does not import it directly. |
| Runtime tokens | `@nebutra/tokens/styles.css` | Import once per app. Components consume semantic/component CSS variables. |
| Primitives | `@nebutra/ui/primitives` or `@nebutra/ui/primitives/canonical` | Use when building product surfaces. Extend through variants before creating siblings. |
| Compositions | `fragment-components` and product patterns | Use for repeated SaaS page sections, not one-off marketing flourishes. |
| Registry | `https://ui.nebutra.com/r/<name>.json` | External copy-paste distribution; npm remains canonical inside this monorepo. |

## Non-Negotiables

1. Component docs must describe the current implementation substrate. Radix, Base UI, native HTML, and custom primitives are not interchangeable labels.
2. Examples must route through public APIs and semantic/component tokens. A demo that pierces an internal child selector is documentation debt.
3. English and Chinese docs stay structurally paired. If a page is public in one locale, it needs a counterpart or an explicit governance exception.
4. Registry items are distribution artifacts, not design authority. The MDX docs and package source define the contract.
