## 概览

`@nebutra/permissions` 在进程内包了一层 [CASL](https://casl.js.org)，做 RBAC/ABAC。它自带：

- **6 个默认角色**：`owner`、`admin`、`member`、`viewer`、`billing_admin`、`guest`
- **action/resource 规则**，不是一份固定的权限范围字符串清单——`{ action: "delete", resource: "Project" }`，可以带 `conditions`（比如 `createdBy: "${user.userId}"`）
- **进程内强制执行**，走 CASL（没有网络往返）
- **React UI 门控**，用 `<Can>` / `<Cannot>`

CASL 是唯一的权限后端——根据
[ADR 2026-09-24 Sailor 收敛](https://github.com/nebutra/nebutra-sailor/blob/main/docs/architecture/2026-09-24-sailor-convergence.md)，
曾经作为图关系授权（Zanzibar 风格）替代方案提供的 OpenFGA 适配器已经删除，没有东西替代它。如果
你需要跨租户共享或超出 CASL 进程内规则表达能力的图关系访问控制，需要自己针对
`@nebutra/permissions` 的接口写一个适配器。

## 默认角色（`packages/iam/permissions/src/roles.ts`）

| 角色 | 描述 |
|------|------|
| `owner` | 完全控制——对所有默认资源都有 create/read/update/delete/manage/invite/publish/export/share |
| `admin` | 继承 `owner` 的规则，唯独不能删除 workspace；`Billing` 只能只读式地 read/update |
| `member` | 对自己创建的资源做 CRUD（`conditions: { createdBy: "${user.userId}" }`）；对分享给自己的资源可以 read/update；可以邀请成员 |
| `viewer` | 只读，而且只能看标记为公开、或者明确分享给自己的资源 |
| `billing_admin` | 继承 `viewer`；可以 create/read/update `Billing`，可以 read `Workspace` |
| `guest` | 只能读取明确分享给自己**且**标记了 `guestAccess: true` 的资源 |

角色可以 `inherit` 另一个角色（`admin` 继承 `owner` 的规则集，减掉一条覆盖；`member` 和
`billing_admin` 继承 `viewer`）。这是"每个角色一套规则"，不是一条从上到下的 4 级线性层级。

## 默认资源与动作

动作（Action）：`create`、`read`、`update`、`delete`、`manage`、`invite`、`publish`、`export`、
`share`（`Action` 类型也接受任意字符串，所以可以加自己的）。

资源（Resource）：`Document`、`Project`、`Workspace`、`User`、`Billing`、`ApiKey`、`Team`、
`Invite`、`Integration`、`AiProviderKey`、`Automation`、`Workflow`（同样可以用字符串扩展）。

这里没有一份固定的 `resource:action` 权限范围字符串目录（`project:delete`、`api_key:create` 之
类）——权限检查始终是一个 `(action, resource, subject?)` 三元组。

## 强制执行

### API 网关（Hono 中间件）

```typescript
import { requirePermission } from "@nebutra/permissions";

// 没有用户上下文返回 401，action/resource 组合被拒绝返回 403
app.delete("/api/projects/:id", requirePermission("delete", "Project"), handler);
```

`requirePermission(action, resource, options?)` 返回 Hono 中间件。`options.extractSubject`
可以传入具体的记录（配合 `createdBy` 这类 `conditions`），而不只是资源类型；
`options.onDenied` 可以自定义 403 响应。

### Server Actions / 手动检查

`requirePermission` 是 Hono 中间件，不是一个独立的断言函数——在 Hono 上下文之外，直接调用
permissions manager：

```typescript
"use server";
import { getPermissions } from "@nebutra/permissions";

export async function deleteProject(projectId: string, user: PermissionContext) {
  const permissions = getPermissions();
  if (!permissions.can(user, "delete", "Project", { id: projectId })) {
    throw new Error("Forbidden");
  }
  // ...
}
```

### React UI 门控

```tsx
import { Can, Cannot } from "@nebutra/permissions/react";

// 只有当前用户能对该资源执行该动作时才渲染 children
<Can action="delete" resource="Project" subject={project}>
  <DeleteButton />
</Can>

// 被拒绝时渲染 fallback
<Can action="update" resource="Billing" fallback={<UpgradePrompt />}>
  <BillingSettings />
</Can>

// Cannot 是反过来的——检查失败时渲染
<Cannot action="create" resource="Project">
  <ReadOnlyBanner />
</Cannot>
```

两者都从包裹应用的 `<PermissionProvider>`（`@nebutra/permissions` 导出为
`PermissionProviderComponent`）读取上下文，也可以直接用 `usePermission(action, resource, subject?)`
这个 hook 做命令式的布尔检查。

## 自定义角色与资源

`packages/iam/permissions/src/roles.ts` 里的 `DEFAULT_ROLES` 是一个普通对象，值是
`RoleDefinition`（`role`、可选的 `inherits`、`description`、`rules: PermissionRule[]`）。加一个
角色就是加一条记录；加一个资源或动作，直接用字符串就行——两种类型都在命名常量之外接受任意
字符串。
