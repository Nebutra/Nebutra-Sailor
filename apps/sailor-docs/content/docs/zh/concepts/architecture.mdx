## 概览

脚手架出来的项目是一个 **Turborepo monorepo**：Next.js 16 应用、Hono API 网关，以及共享的
`@nebutra/*` 包（设计系统、权限、计费、认证……）。根据
[ADR 2026-09-24 Sailor 收敛](https://github.com/nebutra/nebutra-sailor/blob/main/docs/architecture/2026-09-24-sailor-convergence.md)，
`backends/gateway` 是**唯一**应该放业务端点的地方——`apps/web` 的路由处理器被限制在 Next 本身
需要的范围内（认证回调、OG 路由、框架钩子）。

```
浏览器
   │
   ▼
apps/web（Next.js 16）
   ├─ 页面 / Server Components
   └─ app/api/[[...route]]  ──▶  backends/gateway（Hono），进程内挂载
                                   （GATEWAY_MODE=embedded，默认）
                                        │
                           ┌────────────┼────────────┐
                           ▼            ▼             ▼
                      PostgreSQL      Redis        AI 服务商
                     （Prisma，RLS）  （缓存/队列）   （网关）
```

模板不选部署平台——`create-sailor` 实际生成了什么（`Dockerfile.web`、`docker-compose.yml`）以及
内嵌/独立网关的选择，见[部署概览](/zh/deployment/overview)。

## 默认脚手架里的应用

| 应用 | 框架 | 角色 |
|-----|------|------|
| `web` | Next.js 16 | 已认证的产品应用；默认托管网关 |
| `landing` | Next.js 16 | 公开营销站 |
| `auth` | Next.js 16 | Better Auth 登录中心 |
| `mail-preview` | — | 事务性邮件模板的本地预览服务 |
| `backends/gateway` | Hono | 唯一的业务 API |

Nebutra 自己的实例还额外跑着 `studio`（Sanity CMS）和 `storybook`——默认脚手架不包含这两个。

## 核心 packages

| Package | 描述 |
|---------|------|
| `@nebutra/ui` | 组件库——Radix + Nebutra primitives |
| `@nebutra/tokens` | 运行时 CSS 设计 token |
| `@nebutra/auth` | Better Auth 服务端实例 + 服务间 JWT（`signServiceToken` / `verifyServiceToken`） |
| `@nebutra/permissions` | RBAC/ABAC——CASL，进程内 |
| `@nebutra/db` | Prisma 客户端（`getSystemDb`、`getTenantDb`） |
| `@nebutra/tenant` | 租户上下文（`getCurrentTenant`）+ RLS 助手（`withRls`） |
| `@nebutra/billing` | 结账、权益、用量计量 |
| `@nebutra/queue` | QStash，开发环境内存降级 |
| `@nebutra/metering` | 用量计量 → ClickHouse |
| `@nebutra/webhooks` | 内置的出站 Webhook 分发 |

## 请求流程（内嵌网关，默认模式）

```
请求
  │
  ├─ 1. apps/web 接收。更具体的 Next 路由总是优先于 catch-all；
  │     catch-all 只会收到其他路由没匹配上的请求。
  │
  ├─ 2. app/api/[[...route]] 把请求交给进程内构建的 Hono 应用
  │     （backends/gateway，没有后台队列 worker——那部分不管哪种模式
  │     都走 QStash 的 webhook 投递路由）。
  │
  ├─ 3. 网关中间件
  │     ├─ 认证       （Better Auth 会话 Cookie，或服务间调用的 x-service-token）
  │     ├─ 租户        （组织上下文）
  │     ├─ 权限        （CASL）
  │     └─ 限流
  │
  └─ 4. 路由处理器——响应形状由该路由自己的 Zod schema 决定。
        错误统一走 `@nebutra/errors` 的一个封装：
        { error: { code, message, details? }, requestId? }。
```

服务间调用用短期有效的 **HS256 JWT**，放在 `x-service-token` 里，不是老式的 hex-HMAC 方案。
见 [API 认证](/zh/api-reference/authentication)。

## 数据库与行级安全

每张表的访问规则只在一处声明：`packages/platform/db/prisma/schema.prisma` 里的 `/// @rls`
注释——常见情况下从 `tenantId` / `organizationId` 列自动推断。一个 generator 在每次
`prisma generate` 时把它转换成 Postgres RLS 策略；`pnpm db:deploy` 负责应用。见
[数据库概览](/zh/database/overview) 和 [行级安全](/zh/database/rls)——这是模板实际提供的唯一
隔离策略，不是"共享 schema / 每租户一个 schema / 每租户一个数据库"之间的菜单选择。

## AI 层

网关的 AI 路由（经过认证、按租户限定），运行时通过 `nebutra ai` 治理（脚手架阶段不做任何
服务商选择——见 [AI 服务商](/zh/architecture/ai-providers)）：

- `POST /api/v1/ai/chat`
- `POST /api/v1/ai/embeddings`
- `GET /api/v1/ai/models`
- `POST /api/v1/ai/chat/completions`

用量会汇入计量管道，用于配额和计费。

## 认证配置

```bash
# Better Auth 是唯一的认证服务商——没有 Clerk/NextAuth/Supabase 适配器
AUTH_PROVIDER=better-auth
NEXT_PUBLIC_AUTH_PROVIDER=better-auth

# 未配置（没有 BETTER_AUTH_SECRET）时会降级到开发环境的 fallback——见 `nebutra status`
```

在所有共享会话的应用（登录中心、web、landing）之间，保持 `AUTH_PROVIDER` 和
`NEXT_PUBLIC_AUTH_PROVIDER` 一致。
