---
title: API 认证
description: 请求怎么认证——会话 Cookie、服务间 token，以及 AI 服务商 key。
---

没有那种能认证任意网关请求的 `nbk_live_` 风格 API key，也没有 `@nebutra/sdk` 去校验它。真实
存在的是三种互相独立的机制，各自对应不同的调用方：

| 调用方 | 机制 |
|--------|-----------|
| 你自己的前端（已登录用户） | Better Auth 会话 Cookie |
| 另一个内部服务 | `x-service-token`——用 `SERVICE_SECRET` 签的短期 HS256 JWT |
| 按组织划分的 AI 凭据 | `/api/v1/ai/api-keys` 资源 |

## 会话 Cookie（终端用户）

大多数网关路由跑着 `requireAuth` 中间件，读取用户登录时 Better Auth 设置的会话 Cookie。从你自
己的前端发起请求时不需要单独附加 bearer token——网关默认挂载在 `apps/web` 的
`/api/[[...route]]`，同源请求时浏览器会自动带上 Cookie。

## 服务间 token（内部调用方）

对于不是已登录用户的调用方——后台 worker、另一个内部服务——用共享的 `SERVICE_SECRET` 签一个
HS256 JWT，作为 `x-service-token` 发送：

```typescript
import { signServiceToken, verifyServiceToken } from "@nebutra/auth";

const token = signServiceToken({ service: "my-worker" });
```

从 monorepo 之外调用见 [Node.js 快速开始](/zh/quickstart/node) 和
[Python 快速开始](/zh/quickstart/python)。

## AI 服务商 key（按组织）

`/api/v1/ai/api-keys` 让已认证的组织成员签发、列出、修改、吊销该组织 AI 用量对应的凭据——这
是 `ai` 能力下的一个资源，不是通用的 REST API key。管理它仍然需要有效会话
（`requireAuth` + `requireOrganization`）。

```bash
nebutra ai provider list      # 从 CLI 侧查看哪些服务商已启用
```

## 安全最佳实践

<Warning>
  - 永远不要把 `SERVICE_SECRET`、`BETTER_AUTH_SECRET` 或任何服务商 key 提交进源码仓库
  - 所有密钥都用环境变量管理
  - 如果某个部署目标被攻破，轮换 `SERVICE_SECRET`——所有用到它的调用方都需要同步更新
</Warning>
