## 没有托管的 Nebutra API

`backends/gateway`——根据 [ADR 2026-09-24](https://github.com/nebutra/nebutra-sailor/blob/main/docs/architecture/2026-09-24-sailor-convergence.md) 是唯一的业务
API——是**你的**脚手架项目自带的。没有面向第三方客户的 `api.nebutra.com`，没有 `nbk_live_`
风格的 API key 签发，也没有 Nebutra 定义的固定请求/响应封装：每个端点的形状由你自己的 Hono
路由处理器（基于 `@hono/zod-openapi`）决定。

## 跑在哪里

默认情况下网关进程内挂载在 `apps/web` 的 `app/api/[[...route]]`
（`GATEWAY_MODE=embedded`）——跟你的前端同源，一个进程，一次部署。设成
`GATEWAY_MODE=external` 可以让它独立运行；这时 `apps/web` 里没匹配上的 `/api/*` 路径会返回
404。

## 唯一可信来源：OpenAPI

网关自带文档。本地跑起来后打开：

```
GET /docs           # Swagger UI
GET /openapi.json    # 机器可读的规范
```

你项目里定义的每一个路由——它的请求形状、响应形状、认证要求——都是从
`backends/gateway/src/routes/` 里的 Zod schema 生成的，不是可能和代码脱节的手写文档。

## 新增一个端点

```bash
nebutra generate route projects
```

在 `backends/gateway/src/routes/` 里生成一个新的路由文件。业务端点应该放在这里，而不是
`apps/web` 的路由处理器——一个只收紧不放松的棘轮检查（`scripts/lint-route-handlers.mjs`）会在
出现允许列表之外的新路由处理器时让 CI 失败。
