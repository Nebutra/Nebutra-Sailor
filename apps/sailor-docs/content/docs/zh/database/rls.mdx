---
title: 行级安全
description: PostgreSQL RLS 如何在数据库级别强制租户数据隔离，以及 Nebutra 如何通过 Prisma 将其串联起来。
---

行级安全（RLS）是 PostgreSQL 的一个功能，它根据针对每行评估的策略，限制数据库会话可以读取或写入哪些行。Nebutra 使用 RLS 作为多租户数据隔离的主要机制。

## 为什么使用 RLS 而不是应用层过滤

应用层的 `WHERE tenantId = ?` 子句可以工作，但有一个关键弱点：缺少子句会暴露所有租户的数据。RLS 将强制执行移至数据库引擎本身，因此即使没有租户过滤的查询也会自动限制为当前会话允许查看的行。

| 方法 | 强制执行层 | 开发者忘记时的风险 |
|------|-----------|-----------------|
| `WHERE tenantId = ?` | 应用程序代码 | 跨租户完全数据泄露 |
| 行级安全 | PostgreSQL 引擎 | 查询返回空集 — 默认安全 |

## `withRls` 的工作原理

`@nebutra/tenant` 的 `withRls` 返回一个 Prisma 客户端扩展，它：

1. 开启一个 PostgreSQL 事务
2. 将会话本地变量 `app.current_tenant_id` 设置为提供的 `tenantId`
3. 执行查询 — PostgreSQL 使用此变量评估 RLS 策略
4. 完成时清除会话变量

```typescript
import { db } from "@nebutra/db";
import { getCurrentTenant, withRls } from "@nebutra/tenant";

const tenant = getCurrentTenant();
const tenantDb = withRls(db, tenant.tenantId);

// PostgreSQL 强制执行：只返回 WHERE tenant_id = 'org_abc123' 的行
const projects = await tenantDb.project.findMany();
```

在底层，`withRls` 执行：

```sql
SET LOCAL app.current_tenant_id = 'org_abc123';
SELECT * FROM projects;  -- RLS 策略自动过滤
```

## 策略是生成出来的，从不手写

根据 [ADR 2026-09-25 数据库收敛](https://github.com/nebutra/nebutra-sailor/blob/main/docs/architecture/2026-09-25-database-convergence.md)，
`packages/platform/db/prisma/schema.prisma` 是**唯一**由人编辑的文件。每张表的访问规则写成模型
上方的 `/// @rls` 注释——从 `tenantId` / `organizationId` 列或某个单一的租户作用域父关系自动
推断，或者显式声明为以下之一：`global | deny | off | self | via(field) | using(sql) | read(sql) write(sql)`。

一个自定义 Prisma generator（`prisma/generators/rls.mjs`）在每次 `prisma generate` 时，把这些
注释转换成 `generated/rls.sql`——每张表一条策略（`<table>_rls`，或者 `<table>_read` /
`<table>_write` 一对），不带 `TO` 子句：一条策略约束所有既不是表所有者、也没有 `BYPASSRLS` 的
角色。

```prisma packages/platform/db/prisma/schema.prisma
/// @rls off
model Session {
  id       String @id @default(cuid())
  userId   String
  // ...
}
```

`scripts/lint-database.mjs`（接入 `pnpm lint`）会在 `generated/rls.sql` 之外任何地方出现
`CREATE POLICY`，或迁移文件触碰了策略、RLS 开关、函数、grant、role 时让构建失败——迁移文件
只能是结构性变更。

## 应用它：`pnpm db:deploy`

一条命令，适用于任何主机——依次跑 `prisma migrate deploy`，再在一个锁定事务里应用
`platform.sql` + `generated/rls.sql`，最后校验。只要有未应用的迁移、schema.prisma 结构漂移，
或者策略跟 `generated/rls.sql` 不一致，就非零退出。

```bash
pnpm db:deploy    # 迁移，再应用 platform.sql + generated/rls.sql，最后校验
pnpm db:check     # 只读版本——只报告漂移，不实际应用
```

每个部署工作流都把 `db:deploy` 作为第一个 job，跑在应用部署之前——漂移的数据库会直接拦下部署，
而不是让代码跑在跟它不匹配的 schema 上。

## `tenantId` 列约定

存储租户特定数据的每个表都应该包含 `tenantId`（或 `organizationId`）列，这样它的访问规则就能
被自动推断：

```prisma packages/platform/db/prisma/schema.prisma
model Project {
  id          String   @id @default(cuid())
  name        String
  tenantId    String                         // ← 推断出的访问规则；不需要 /// @rls
  createdAt   DateTime @default(now())
  updatedAt   DateTime @updatedAt

  @@index([tenantId])                        // ← 性能要求必须有索引
}
```

<Warning>
永远不要在大型表上省略 `@@index([tenantId])`。没有索引，PostgreSQL 会在每次 RLS 策略检查时执行全表扫描，随着数据增长，查询性能会显著下降。
</Warning>

## 为管理操作绕过 RLS

某些操作 — 例如跨租户分析、计费任务或管理员控制台 — 需要查询所有租户。为这些操作使用具有 `BYPASSRLS` 权限的单独数据库角色，而不是应用程序服务角色。

```typescript packages/platform/db/src/admin.ts
// 管理员客户端 — 完全绕过 RLS
// 仅用于内部后台任务和管理工具
export const adminDb = new PrismaClient({
  datasources: {
    db: { url: process.env.DATABASE_ADMIN_URL },
  },
});
```

<Warning>
永远不要通过面向用户的 API 路由暴露 `adminDb` 客户端。它绕过所有租户隔离。将其限制在后台工作器、定时任务和内部管理工具中。
</Warning>

## 性能：`tenantId` 上的索引

RLS 策略为每个查询添加 `tenant_id` 过滤。为使其快速执行，PostgreSQL 需要该列上的索引。始终在 Prisma 架构中添加 `@@index([tenantId])`，这会生成：

```sql
CREATE INDEX "projects_tenant_id_idx" ON "projects"("tenant_id");
```

对于几乎总是同时按 `tenantId` 和另一列（例如 `status`）查询的表，使用复合索引：

```prisma
@@index([tenantId, status])
```

## 验证 RLS 是否已激活

要确认表已启用 RLS 并应用了策略，在数据库中运行此查询：

```sql
-- 检查所有租户作用域表的 RLS 状态
SELECT
  tablename,
  rowsecurity AS rls_enabled,
  forcerowsecurity AS rls_forced
FROM pg_tables
WHERE schemaname = 'public'
ORDER BY tablename;

-- 列出特定表上的所有策略
SELECT policyname, cmd, qual, with_check
FROM pg_policies
WHERE tablename = 'projects';
```
