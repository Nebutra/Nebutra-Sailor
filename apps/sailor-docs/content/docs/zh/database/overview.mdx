Nebutra-Sailor 用 **Prisma** 做 ORM，**PostgreSQL** 做数据库引擎——一处来源，生成式产出，先部署
再上线。完整决策见 [ADR 2026-09-25 数据库收敛](https://github.com/nebutra/nebutra-sailor/blob/main/docs/architecture/2026-09-25-database-convergence.md)；这页讲日常
怎么用。

## 架构

```
┌─────────────────────────────────────┐
│            应用程序代码              │
│  (Next.js Server Components, API)   │
└────────────────┬────────────────────┘
                 │ import { db } from "@nebutra/db"
┌────────────────▼────────────────────┐
│            Prisma 客户端             │
│       （类型安全的查询构建器）        │
└────────────────┬────────────────────┘
                 │ PostgreSQL 协议
┌────────────────▼────────────────────┐
│         PostgreSQL 数据库           │
│  pgvector · 生成式 RLS              │
└─────────────────────────────────────┘
```

`packages/platform/db/prisma/schema.prisma` 是**唯一来源**：所有表，以及每张表的访问规则（写
成 `/// @rls` 注释）。其余的一切——`generated/rls.sql`、baseline 迁移——都是从它生成的，或者在
每次部署（`pnpm db:deploy`）时重新应用到它上面。脚手架阶段没有数据库选择这一说；
`create-sailor` 每次都写出同一份 schema。

## 架构布局

只有两个 Postgres schema——为什么见 [Prisma Postgres Schemas](/zh/architecture/multi-schema)：

| PostgreSQL schema | 用途 |
|----------------|------|
| `public` | 所有应用表 |
| `better_auth` | Better Auth 自己的插件（`organization`、`passkey` 等）管理的表 |

这不是"每个产品域一个 schema"的拆分方式——没有 `ecommerce`、`recsys` 或 `web3` schema，也没有
可以裁剪掉某个 schema 的脚手架 flag。

## pgvector

PostgreSQL 的 `pgvector` 扩展支撑着 AI 嵌入检索（`@nebutra/search`，pgvector 加全文检索——没有
单独的搜索引擎）。自托管 PostgreSQL 在运行迁移之前需要执行 `CREATE EXTENSION vector;`；
`create-sailor` 接好的 `postgres:15-alpine` 镜像已经带了这个扩展。

## 命令参考

| 命令 | 使用时机 |
|------|---------|
| `pnpm db:deploy` | **部署命令。** 跑未应用的迁移，再应用 `platform.sql` + `generated/rls.sql`，最后校验。出现漂移就非零退出。 |
| `pnpm db:check` | `db:deploy` 的只读版本——只报告漂移，不实际应用 |
| `pnpm db:generate` | 编辑 `schema.prisma` 后——重新生成 Prisma 客户端和 `generated/rls.sql` |
| `pnpm db:migrate` | 创建并应用新迁移（本地开发） |
| `pnpm db:push` | 不生成迁移文件直接推送 schema 变更（仅限本地原型开发） |
| `pnpm db:studio` | 打开 Prisma Studio |
| `pnpm db:seed` | 用开发种子数据填充数据库 |

<Warning>
永远不要对生产或预发布数据库运行 `pnpm db:push`。它在没有迁移历史记录的情况下应用 schema 变更，可能导致不可逆的数据丢失。生产部署用 `pnpm db:deploy`。
</Warning>

## 多租户

一张表的访问规则从它的 `tenantId` / `organizationId` 列推断（或者显式声明）。查询通过
`@nebutra/tenant` 的 `withRls` 助手，用 PostgreSQL 行级安全（RLS）自动限定范围。详情见
[RLS 指南](/zh/database/rls)。
