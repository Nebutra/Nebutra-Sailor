## 模板不选平台

根据 [ADR 2026-06-04，生产运行时闭环](https://github.com/nebutra/nebutra-sailor/blob/main/docs/architecture/2026-06-04-production-runtime-closure.md)
和 [ADR 2026-09-24，Sailor 收敛](https://github.com/nebutra/nebutra-sailor/blob/main/docs/architecture/2026-09-24-sailor-convergence.md)
§5：模板只提供 Next `standalone` 构建和 Dockerfile，`create-sailor` 不问你要跑在哪。脚手架出来的
项目里没有 `--deploy vercel|railway|cloudflare` 这样的 flag，也没有 `DEPLOY_TARGET_*` 选择器，
不内置任何特定平台的配置。下面讲的是代码实际给你的东西——不是某家公司自己的生产配置。

## create-sailor 生成了什么

| 文件 | 用途 |
|------|------|
| `Dockerfile.web` | `apps/web` 的多阶段构建（Next `output: "standalone"`）——默认的部署单元，因为网关就挂载在它里面 |
| `docker-compose.yml` | `web` + 本地 `postgres` + `redis`，一条命令跑起本地或单机栈 |
| `backends/gateway/Dockerfile` | 网关的独立镜像，供你把网关单独跑（见下文） |

任何能跑 Docker 镜像或 `node server.js` 进程的主机都可以：一台 VM、Fly、Railway、Render、ECS、
Kubernetes 集群，或者像 Vercel 这样能直接构建 Next.js 的平台（见 [Vercel](/zh/deployment/vercel)）。

## 网关：内嵌还是独立

`backends/gateway`（Hono）是唯一的业务 API。默认情况下它进程内挂载在 `apps/web` 的
`app/api/[[...route]]/route.ts`：

```bash
GATEWAY_MODE=embedded   # 默认——一个进程，一个源，一次部署
GATEWAY_MODE=external   # apps/web 对每个没匹配上的 /api/* 路径返回 404，什么都不挂载；
                         # 你自己构建并运行 backends/gateway（它自己的 Dockerfile）独立部署
```

只有当你真的需要网关和前端独立扩缩容或部署时才选 `external`。模板本身不强制要求这样做。

## 部署前：`pnpm db:deploy`

在新版本应用开始对外服务之前运行——它会应用未执行的迁移，再应用 `platform.sql` + 生成式 RLS
策略，最后校验数据库跟 `schema.prisma` 是否一致，出现任何漂移就非零退出：

```bash
pnpm db:deploy
```

这条命令具体做了什么见 [数据库概览](/zh/database/overview) 和 [行级安全](/zh/database/rls)。
不管你的部署流水线怎么搭，这一步都应该在应用启动之前，而不是之后——`db:migrate`
（`prisma migrate dev`）只用于本地开发。

## 环境变量

每个必需的变量在启动时都会被校验，缺失时会直接失败并给出清晰的错误信息——完整参考见
[环境变量](/zh/configuration/environment-variables)。生产部署至少需要 `DATABASE_URL`、
`BETTER_AUTH_SECRET`、`BETTER_AUTH_URL` / `NEXT_PUBLIC_AUTH_URL` 和 `SERVICE_SECRET`。
