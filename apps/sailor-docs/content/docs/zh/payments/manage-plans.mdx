---
title: 管理计划
description: 创建 Stripe 产品、在代码中配置计划限额，并为 Nebutra 添加新的账单层级。
---

<Note>
计划层级（FREE/PRO/ENTERPRISE）是订阅概念，目前仍映射到 **Stripe** 产品（历史遗留，根据 [ADR 2026-09-26](https://github.com/Nebutra/Nebutra-Sailor/blob/main/docs/architecture/2026-09-26-creem-global-payments.md)）。这与一次性卡支付结账是两回事，后者运行在 **Creem** 上——参见 [Creem 集成](/zh/integrations/creem)。
</Note>

## 前置条件

- 拥有 API 访问权限的 Stripe 账户
- 已配置环境变量（参见[账单概览](/zh/payments/overview)）
- 已安装 Stripe CLI：`npm install -g stripe`

## 第一步：在 Stripe 中创建产品

每个账单层级对应一个 Stripe 产品及一个或多个价格。可通过 Stripe CLI 或 Dashboard 界面创建。

<Tabs>
  <Tab title="Stripe CLI">
    ```bash
    # 创建 PRO 产品
    stripe products create \
      --name="Nebutra PRO" \
      --description="每月 100,000 次 API 调用，10 个成员，邮件支持"

    # 为 PRO 创建每月循环价格（$49/月）
    stripe prices create \
      --product=prod_REPLACE_WITH_PRO_ID \
      --unit-amount=4900 \
      --currency=usd \
      --recurring[interval]=month \
      --nickname="PRO Monthly"

    # 创建 ENTERPRISE 产品（自定义定价 — 手动设置价格）
    stripe products create \
      --name="Nebutra ENTERPRISE" \
      --description="无限量，SSO，SLA，自定义合同"
    ```
  </Tab>
  <Tab title="Stripe Dashboard">
    1. 进入 **Stripe Dashboard → Products → Add product**。
    2. 为每个层级填写名称、描述和定价。
    3. 将每个层级的**价格 ID**（`price_...`）复制到 `.env` 文件中。
  </Tab>
</Tabs>

## 第二步：设置价格 ID 环境变量

在 Stripe 中创建价格后，记录其 ID——每个计费周期一个，与 `packages/commerce/billing/src/catalog/checkout-plan.ts` 对应：

```bash
STRIPE_PRICE_ID_PRO_MONTHLY=price_xxxxxxxxxxxxxxxxxxxx
STRIPE_PRICE_ID_PRO_YEARLY=price_xxxxxxxxxxxxxxxxxxxx
STRIPE_PRICE_ID_ENTERPRISE_MONTHLY=price_xxxxxxxxxxxxxxxxxxxx
STRIPE_PRICE_ID_ENTERPRISE_YEARLY=price_xxxxxxxxxxxxxxxxxxxx

# 每个计划可选的试用期覆盖
STRIPE_TRIAL_DAYS_PRO=14
STRIPE_TRIAL_DAYS_ENTERPRISE=0
```

`resolveCheckoutOffer` 会直接从这些环境变量中，按 `{ plan, interval }` 组合读取对应的价格 ID——不存在一张需要手动维护结账价格的硬编码表。

## 第三步：配置计划限额与功能

计划配额与功能门控**不是**一个静态文件——而是 `PlanConfigService`（`packages/commerce/billing/src/config/plan-config.ts`），一个数据库驱动、Redis 缓存的配置，以 `plan: "FREE" | "PRO" | "ENTERPRISE"` 为键，并带有 `version` 字段用于在你修改限额时为存量客户保留原有条款。每条 `PlanConfig` 记录都持有 `features`（`Record<string, FeatureValue>`）和 `limits`（`Record<string, LimitConfig>`——`limit: -1` 表示无限制）。

真正属于代码的，是每个计划所依赖的功能权益清单——`packages/commerce/billing/src/entitlements/service.ts`：

```typescript packages/commerce/billing/src/entitlements/service.ts
export const FEATURES = {
  // requireFeature() 检查的功能键——如 "ai.chat"、"ai.embeddings"、"api.access"
} as const;

export const PLAN_FEATURES: Record<Plan, FeatureKey[]> = {
  FREE: [/* … */],
  PRO: [/* … */],
  ENTERPRISE: [/* … */],
};
```

## 第四步：检查某项功能权益

在后端代码的任意位置使用 `@nebutra/billing` 的 `isPlanFeature` 或 `checkEntitlement`：

```typescript
import { isPlanFeature, checkEntitlement } from "@nebutra/billing";

const allowed = isPlanFeature("PRO", "ai.chat");
// → true/false，来自静态的 PLAN_FEATURES 表

const result = await checkEntitlement(organizationId, "ai.chat");
// → 同时会考虑按组织的授权/覆盖项，而不只是计划的默认值
```

API 网关通过 `requireFeature` 中间件（`backends/gateway/src/middlewares/entitlements.ts`）在边缘层执行这一检查：

```typescript
app.post("/api/v1/ai/generate", requireFeature("ai.images", 1), handler);
```

## 添加新计划层级

<Steps>
  <Step title="在 Stripe 中创建产品和价格">
    通过 Stripe CLI 或 Dashboard 创建新产品和价格，并复制价格 ID。
  </Step>
  <Step title="将价格 ID 添加到环境变量">
    ```bash
    STRIPE_PRICE_ID_TEAMS_MONTHLY=price_xxxxxxxxxxxxxxxxxxxx
    ```

    `catalog/checkout-plan.ts` 中的 `CHECKOUT_PLANS` 目前是 `["pro", "enterprise"]`——新增层级也需要在此添加一项，结账逻辑才能解析出它的价格 ID。
  </Step>
  <Step title="添加该计划的配置记录">
    在数据库中新增或更新对应的 `PlanConfig` 记录（不是源码文件），填入新计划的 `limits` 与 `features`。
  </Step>
  <Step title="将计划加入 PLAN_FEATURES">
    ```typescript packages/commerce/billing/src/entitlements/service.ts
    export const PLAN_FEATURES: Record<Plan, FeatureKey[]> = {
      // …
      TEAMS: ["ai.chat", "ai.embeddings", "api.access"],
    };
    ```
  </Step>
</Steps>

## 更新计划限额

计划限额存放在数据库中（`PlanConfigService`），并有 Redis 缓存——不在源码文件里——因此修改限额不需要重新部署。`PlanConfig.version` 支持为存量客户保留原有条款：某个客户处于激活状态的 `planVersion` 覆盖项会让他们继续沿用注册时的限额，直到你主动迁移。

<Note>
租户所处的计划本身（订阅状态）在收到并处理 Stripe Webhook 后立即更新——参见[Webhooks](/zh/payments/webhooks)。不存在轮询延迟。
</Note>
