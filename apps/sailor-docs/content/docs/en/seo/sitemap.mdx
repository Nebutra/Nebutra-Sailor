## How the sitemap works

The sitemap is generated by the Next.js App Router file-system convention, but it's **sharded one child per route locale** rather than a single flat file — with 34 product locales, one giant sitemap would make Search Console report indexing health as one undifferentiated blob. `generateSitemaps()` returns one shard id per locale from the routing SSOT, and Next serves each at `/sitemap/<locale>.xml`.

**File location:**
```
apps/landing/src/app/sitemap.ts
```

## Sharded, per-locale sitemap

```typescript apps/landing/src/app/sitemap.ts (excerpt)
import type { MetadataRoute } from "next";
import { routing } from "@/i18n/routing";
import { SEO_ROUTE_REGISTRY, localesForPath } from "@/lib/seo/route-registry";
import { getSiteUrl } from "@/lib/seo/site-routes";

// One shard per route locale — Next serves them at /sitemap/<locale>.xml.
export function generateSitemaps(): Array<{ id: string }> {
  return routing.locales.map((id) => ({ id }));
}

// Next 16 hands the shard id in as a Promise — read it as a bare string and
// every shard silently comes back empty.
export default async function sitemap({
  id,
}: {
  id: Promise<string | undefined> | string | undefined;
}): Promise<MetadataRoute.Sitemap> {
  const locale = await id;
  if (!locale || !routing.locales.includes(locale)) return [];

  const baseUrl = getSiteUrl();
  const entries: MetadataRoute.Sitemap = [];

  for (const route of SEO_ROUTE_REGISTRY) {
    if (!localesForPath(route.pattern).includes(locale)) continue;
    entries.push({
      url: `${baseUrl}/${locale}${route.pattern}`,
      changeFrequency: route.changeFrequency,
      priority: route.priority,
    });
  }

  return entries;
}
```

Static route metadata (`changeFrequency`, `priority`, which locales a route publishes in) lives in `SEO_ROUTE_REGISTRY` (`apps/landing/src/lib/seo/route-registry.ts`), not hardcoded per-route in `sitemap.ts` — add a new page there, not by editing the sitemap function.

Blog posts come from `getAllPosts()` in `@/lib/blog` (not Sanity's client directly), folded into the registry-driven entries above rather than appended as a separate static list.

Next emits **no index** for a sharded sitemap — the `<sitemapindex>` at `/sitemap.xml` is hand-written in `app/sitemap-index.xml/route.ts` and rewritten onto that path by `next.config.ts`, since a route file there would collide with the `sitemap.ts` metadata file.

## Robots.txt

The `robots.ts` file controls which paths crawlers can access. It also declares a narrower allow-list for named AI/answer-engine crawlers (GPTBot, ClaudeBot, Google-Extended, Applebot-Extended, CCBot, Bytespider) that only see the product surface, not the full site:

```typescript apps/landing/src/app/robots.ts (excerpt)
import type { MetadataRoute } from "next";
import { getSiteUrl } from "@/lib/seo/site-routes";

export default function robots(): MetadataRoute.Robots {
  const baseUrl = getSiteUrl();
  return {
    rules: [
      {
        userAgent: "*",
        allow: "/",
        disallow: ["/api/", "/_next/", "/sign-in", "/sign-up", "/admin/", "/settings/"],
      },
      ...(["GPTBot", "ClaudeBot", "Google-Extended", "Applebot-Extended", "CCBot", "Bytespider"] as const).map(
        (userAgent) => ({
          userAgent,
          allow: ["/", "/blog/", "/features", "/features/", "/pricing", "/llms.txt"],
          disallow: ["/api/", "/_next/", "/sign-in", "/sign-up", "/admin/", "/settings/"],
        })
      ),
    ],
    sitemap: `${baseUrl}/sitemap.xml`,
    host: baseUrl,
  };
}
```

<Warning>
  Never include authenticated app routes (e.g., `app.nebutra.com/dashboard`) in the sitemap. Only the public landing page (`nebutra.com`) is indexed. The `apps/web` and `apps/sailor-docs` apps each have their own `robots.ts`.
</Warning>

## Verifying the sitemap locally

```bash
pnpm --filter @nebutra/landing dev
# Visit: http://localhost:3000/sitemap/en.xml
# Visit: http://localhost:3000/robots.txt
```

The sitemap is rendered on demand in development and cached at the CDN edge in production.

## Submitting to Google Search Console

<Steps>
  <Step title="Verify ownership of your domain">
    In [Google Search Console](https://search.google.com/search-console), add your property (`https://nebutra.com`) and verify ownership via DNS TXT record or the HTML file method.
  </Step>
  <Step title="Submit your sitemap">
    In Search Console, go to **Sitemaps** in the left sidebar. Enter `sitemap.xml` in the URL field and click **Submit**.
  </Step>
  <Step title="Monitor indexing status">
    After submission, Search Console shows how many URLs have been discovered and indexed. It typically takes 24–72 hours for a new sitemap to be processed.
  </Step>
  <Step title="Re-submit after major content updates">
    Google recrawls sitemaps automatically, but after a major release (new locale, large number of new blog posts), manually re-submitting speeds up re-indexing.
  </Step>
</Steps>

## Sitemap size limits

Google supports sitemaps of up to 50,000 URLs or 50 MB (uncompressed) per file — sharding by locale (above) already keeps each shard well under that for 34 locales' worth of pages. If a single locale's shard ever approaches the limit (a very large blog, for instance), shard that locale further the same way: a nested `generateSitemaps()` keyed by a secondary id (e.g. post-batch) alongside the locale id, with the hand-written index in `app/sitemap-index.xml/route.ts` updated to list the extra children.
