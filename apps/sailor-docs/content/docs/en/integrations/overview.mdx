Nebutra-Sailor distinguishes between:

- **user-managed integrations** exposed in the product UI
- **platform services** that power the stack but are not registered through a
  generic `defineIntegration()` API

## User-managed integrations

The current integrations page in the web app works with these types:

- `SHOPIFY`
- `SHOPLINE`
- `STRIPE`
- `CUSTOM`

See the live product surface in:

```text
apps/web/src/app/[locale]/(app)/integrations/page.tsx
```

The backing API lives in:

```text
backends/gateway/src/routes/integrations/index.ts
```

## Platform services

These are important parts of the stack, but they are **not** registered through
a fictional `@nebutra/integrations` package:

| Service | Role |
| --- | --- |
| Resend / email | Transactional email infrastructure |
| Sanity | Content management and editorial data |
| Sentry | Error monitoring |
| Vercel | Deployment target |

Treat them as platform dependencies or provider-specific packages, not as rows
inside an abstract integration registry API unless the codebase actually models
them that way.

## Current route/API model

The gateway exposes CRUD for integrations under `/api/v1/integrations` and
stores credentials/settings through the encrypted integration model.

Example browser call:

```typescript
import { browserApiClient } from "@/lib/api/client";

const { data } = await browserApiClient.GET("/api/v1/integrations");
```

## Adding a new managed integration

Today, adding a new integration means updating the real gateway + UI surfaces:

1. Extend the integration type/schema in `backends/gateway/src/routes/integrations/index.ts`.
2. Update the UI catalog in `apps/web/src/app/[locale]/(app)/integrations/page.tsx`.
3. If secrets are required, keep them in the encrypted `integration.credentials`
   / `integration.settings` fields handled by the DB layer.

Do not document or import a nonexistent:

- `@nebutra/integrations`
- `defineIntegration(...)`
- a dedicated web-app integration registry file
