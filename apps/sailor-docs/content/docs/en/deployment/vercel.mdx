title: Vercel
description: Deploying the scaffolded Next.js apps on Vercel — nothing platform-specific required.
---

The template doesn't pick Vercel, or rule it out. `apps/web`, `apps/landing`, and `apps/auth` are
plain Next.js 16 apps; Vercel builds a Next.js app directly (it doesn't need the `standalone`
output the Docker path uses — that's specifically for self-hosting outside a platform that already
knows how to run Next).

<Note>
  This is a general "the code doesn't block it" guide, not a maintained runbook — Nebutra's own
  instance doesn't run on Vercel. There's no `nebutra`-specific Vercel integration, project preset,
  or CLI wrapper; you configure it the same way you would for any Next.js app.
</Note>

## What works out of the box

- **The embedded gateway.** `app/api/[[...route]]/route.ts` (`GATEWAY_MODE=embedded`, the default)
  is a normal Next.js route handler with `export const runtime = "nodejs"` — Vercel runs it as a
  serverless function like any other route. No separate API deployment needed.
- **Environment variables.** Set them in the Vercel project's Environment Variables settings the
  same way you'd set `.env.production` anywhere else — see
  [Environment Variables](/configuration/environment-variables).

## What to check before you deploy

- **The build command.** Confirm your project's `apps/web` (and any other app you deploy) actually
  produces a Next.js build with its `build` script. If your project has customized `apps/web` to
  build with something other than `next build` by default, set the Vercel project's Build Command
  to the Next-producing script explicitly (e.g. `pnpm --filter @nebutra/web run build:next` if
  that's what your project defines) rather than relying on the default.
- **Root Directory.** In a Turborepo monorepo, point Vercel's Root Directory at the app
  (`apps/web`, `apps/landing`, …) and let it detect the workspace.
- **`pnpm db:deploy` still runs separately.** Vercel doesn't run your database migrations for you —
  run `pnpm db:deploy` against production `DATABASE_URL` as its own step (a GitHub Action, a
  release step, or by hand) before traffic hits the new deployment. See
  [Deployment Overview](/deployment/overview).
- **`GATEWAY_MODE=external`, if you use it, needs its own host.** Vercel serverless functions are
  not a place to run the gateway standalone (no long-lived process, no background queue workers) —
  keep `GATEWAY_MODE=embedded` for a Vercel deploy, or host `backends/gateway` somewhere else
  entirely.
