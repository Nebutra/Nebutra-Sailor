## Deployment options

| Option | Best for | Complexity | Cost |
|--------|---------|-----------|------|
| **Vercel** | Most teams | Low | Usage-based |
| **Docker (self-hosted)** | Data residency, compliance | Medium | Infrastructure cost |
| **Standalone API** | Custom infra, Hono-only | Medium | Infrastructure cost |

## Production architecture

```
User
  │
  ▼
Vercel Edge Network (CDN, WAF, DDoS protection)
  │
  ├─── apps/landing-page   nebutra.com          (Next.js on Vercel)
  │
  ├─── apps/web            app.nebutra.com      (Next.js on Vercel)
  │         │
  │         │ REST / Server Actions
  │         ▼
  └─── apps/api-gateway    api.nebutra.com      (Hono on Vercel Functions)
              │
              ├─── PostgreSQL (Supabase / Neon / RDS)
              ├─── Redis     (Upstash / ElastiCache)
              └─── ClickHouse (ClickHouse Cloud / self-hosted)
```

## Before you deploy

### Run database migrations

Always run migrations **before** deploying a new app version. The app will fail to start if the schema is behind the migration state.

```bash
pnpm db:migrate
```

In CI/CD this is handled automatically by the `deploy.yml` GitHub Actions workflow, which runs migrations as a pre-deploy step.

### Validate environment variables

All required environment variables are validated by `@nebutra/config` at startup. A missing required variable causes a hard crash with a descriptive error — no silent failures. Run a local validation pass before pushing:

```bash
pnpm typecheck
```

## Environment variable management

<Tabs>
  <Tab title="Vercel">
    Set environment variables in the Vercel dashboard under **Settings → Environment Variables**. Vercel supports separate values for Production, Preview, and Development environments.

    For secrets shared across multiple Vercel projects, use [Vercel Shared Environment Variables](https://vercel.com/docs/environment-variables/shared).
  </Tab>
  <Tab title="Docker">
    Pass environment variables via a `.env` file or Docker Compose `environment:` block. Never commit `.env` files with real secrets to source control.

    For production, use Docker Secrets or a secrets manager (AWS Secrets Manager, HashiCorp Vault).
  </Tab>
</Tabs>

## CI/CD with GitHub Actions

The repository ships 14 workflows in `.github/workflows/`:

| Workflow | Trigger | What it does |
|----------|---------|-------------|
| `ci.yml` | Every push + PR | lint → typecheck → build → test → e2e → coverage |
| `deploy.yml` | Push to `main` | Run migrations → deploy to Vercel |
| `docker-build-push.yml` | Push to `main` | Build and push Docker images to registry |
| `security-scan.yml` | Push + schedule | CodeQL static analysis + dependency audit |

<Note>
  The `deploy.yml` workflow requires `VERCEL_TOKEN`, `VERCEL_ORG_ID`, and per-app `VERCEL_PROJECT_ID_*` secrets to be configured in the GitHub repository settings.
</Note>

## Zero-downtime deploys

Vercel handles zero-downtime deployments automatically. New deployments are only promoted to production after a successful health check. Rollback is instant — click "Promote" on any previous deployment in the Vercel dashboard.

For Docker self-hosted deployments, configure a reverse proxy (nginx, Caddy) with rolling restarts or use Docker Swarm / Kubernetes for zero-downtime rolling updates.
