## How to use this checklist

Work through each section before your first production launch and before every major release. Items marked as critical must be resolved before going live.

---

## Infrastructure

**All environment variables configured and validated**

Every required environment variable must be set wherever you're deploying (your platform's
dashboard, a Docker Compose env file, or a secrets manager). `@nebutra/config` validates them at
startup and crashes with a descriptive error if any are missing.

**`pnpm db:deploy` run against the production database, before the new app version starts serving**

```bash
DATABASE_URL=<your-production-db-url> pnpm db:deploy
```

This applies pending migrations, then `platform.sql` + the generated RLS policies, then verifies
the database matches `schema.prisma` — it exits non-zero on any drift. See
[Row-Level Security](/database/rls). `db:migrate` (`prisma migrate dev`) is for local development
only; never run it against production.

**PostgreSQL backup strategy configured**

Enable automated daily backups with at least 7-day retention. Verify that a test restore works. If using Supabase or Neon, enable Point-in-Time Recovery (PITR).

**Redis persistence configured**

Enable AOF (Append Only File) persistence on Redis if you rely on it for caching or rate-limit
state. The queue (QStash) does not use Redis — it is a separate, always-persistent serverless
queue, so there are no in-flight queue jobs to lose on a Redis restart.

## Payments

**Creem webhook configured and verified**

In the Creem dashboard, create a webhook pointing to `https://yourdomain.com/api/webhooks/creem` (or your standalone gateway's host, if `GATEWAY_MODE=external`). Add the signing secret as `CREEM_WEBHOOK_SECRET`, and set `CREEM_API_KEY` / `CREEM_PRODUCT_ID`. Verify delivery in staging with `CREEM_TEST_MODE=true` before flipping to live keys. See the [Creem integration guide](/integrations/creem).

**Stripe webhooks configured and verified (legacy — subscriptions)**

Stripe is retired from new work, but subscriptions, the billing portal, and pre-switch checkouts still depend on it. In the Stripe dashboard, create a webhook endpoint pointing to `https://yourdomain.com/api/webhooks/stripe`. Add the webhook signing secret as `STRIPE_WEBHOOK_SECRET`. Use `stripe listen --forward-to` to verify delivery in staging.

**Required Stripe events enabled (legacy)**

Ensure the following events are selected on the webhook endpoint:
- `customer.subscription.created`
- `customer.subscription.updated`
- `customer.subscription.deleted`
- `invoice.payment_succeeded`
- `invoice.payment_failed`
- `checkout.session.completed`

## Authentication

**Better Auth (default) wired across auth center + app**

- `AUTH_PROVIDER` / `NEXT_PUBLIC_AUTH_PROVIDER` = `better-auth`
- `BETTER_AUTH_URL` / `NEXT_PUBLIC_AUTH_URL` point at the login center host
- `BETTER_AUTH_SECRET` identical on auth + web
- `AUTH_COOKIE_DOMAIN` is the shared parent domain (e.g. `.nebutra.com`)
- OAuth redirect URIs include the auth-center callback paths

Better Auth is the only auth provider — the Clerk, NextAuth, and Supabase adapters were deleted
per the Sailor Convergence ADR (2026-09-24). There is no Clerk webhook path to wire up.

## Networking

**Custom domain configured**

Point your domain at wherever you deployed to — a platform like Vercel handles this in its
dashboard; a self-hosted Docker deploy needs your own DNS + reverse proxy setup. See
[Deployment Overview](/deployment/overview).

**SSL/TLS active**

Confirm HTTPS is enforced on all domains. Platforms like Vercel handle this automatically. On
Docker self-hosted, verify your reverse proxy (Caddy / nginx + certbot) is terminating TLS
correctly.

**HTTPS redirect configured**

All HTTP traffic should redirect to HTTPS with a 301. Verify with:

```bash
curl -I http://yourdomain.com
# Expect: HTTP/1.1 301 Moved Permanently
# Location: https://yourdomain.com
```

## Security

**Rate limiting tested under load**

The API gateway enforces per-tenant rate limits via Redis. Verify the limits are appropriate for your plan tiers and that the `429 Too Many Requests` response is handled gracefully in your frontend.

**Security scan passed**

The `security-scan.yml` GitHub Actions workflow runs CodeQL static analysis and dependency vulnerability scanning. Confirm the latest scan on `main` passed with no critical findings.

**No secrets committed to source control**

Run a secrets scan before launch:

```bash
git log --all --diff-filter=A -- '*.env*'   # check for committed .env files
```

Use tools like `trufflehog` or GitHub's secret scanning feature for a thorough audit.

## Observability

**Sentry error tracking configured**

Set `NEXT_PUBLIC_SENTRY_DSN` and `SENTRY_AUTH_TOKEN` in all app environments. Verify that a test error appears in your Sentry project.

**Monitoring alerts configured**

Set up uptime monitoring (e.g. Better Uptime, Checkly) for:
- `https://yourdomain.com` (landing page)
- wherever you host the web app (`GATEWAY_MODE=embedded`: same domain; `external`: your gateway host)
- `/api/misc/health` on the gateway — see [Docker Deployment](/deployment/docker) for the response shape

Alert on HTTP 5xx rates exceeding 1% or P95 response time above 2 seconds.

**Structured logging verified**

Confirm `@nebutra/logger` output is flowing to your log aggregator (Axiom, Datadog, Cloudwatch). Check that `tenant_id` and `request_id` fields are present in API logs.

## Analytics and compliance

**Analytics configured**

`@nebutra/analytics` (powered by Dub.co) requires the following environment variables:

| Variable | Required | Description |
|----------|----------|-------------|
| `DUB_API_KEY` | Yes | API key from [app.dub.co/settings/tokens](https://app.dub.co/settings/tokens) |
| `DUB_WORKSPACE_ID` | Recommended | Your Dub.co workspace ID (avoids per-request lookups) |
| `DUB_DEFAULT_DOMAIN` | No | Default short-link domain, defaults to `dub.sh` |

Verify by calling `analytics.getWorkspaceStats()` from a test script.

**GDPR / privacy policy live**

A privacy policy must be publicly accessible at `/privacy` (or a linked URL) before accepting user data from EU residents.

**Terms of service live**

Terms of service must be accessible at `/terms` before processing payments.

**Cookie consent configured**

If you track users with analytics or advertising cookies in the EU, a cookie consent banner is required. Verify it appears for users in EU regions.

## Performance

**Performance tested with Lighthouse**

Run Lighthouse against your production domain and target:
- Performance: 90+
- Accessibility: 95+
- Best Practices: 100
- SEO: 100

```bash
npx lighthouse https://yourdomain.com --view
```

**Core Web Vitals passing**

Verify in Google Search Console or Vercel Analytics that LCP, FID, and CLS are in the "Good" range for real user data after the first week of traffic.

## Final sign-off

<Warning>
  Do not go live until all items in the **Infrastructure**, **Payments**, **Authentication**, and **Networking** sections are complete. The remaining sections should be addressed within the first week after launch.
</Warning>
