title: Database Providers
description: Connecting Nebutra to Neon or Supabase — environment variables, connection pooling, and migration setup for each provider.

Nebutra supports two managed PostgreSQL providers out of the box. Both are fully compatible with Prisma v7, pgvector, and RLS. The application code is identical regardless of which provider you choose — only the connection strings differ.

<Note>
Both Neon and Supabase are PostgreSQL. Migrations generated by `pnpm db:migrate` work unchanged on either provider.
</Note>

<Warning>
MySQL-based providers (PlanetScale, Railway MySQL) are **not supported**. Nebutra depends on pgvector and native PostgreSQL RLS — both require PostgreSQL.
</Warning>

<Tabs>
  <Tab title="Neon (default)">
    Neon is the default provider. It is a serverless PostgreSQL platform with branching, auto-suspend, and a generous free tier. PgBouncer connection pooling is built in.

    ### Why Neon

    - **Branching** — create an isolated database branch for each feature branch or PR, with zero data-copy cost
    - **Serverless** — scales to zero when idle; no compute charge for dormant databases
    - **Auto-suspend** — free tier databases pause after 5 minutes of inactivity and resume in ~500 ms
    - **pgvector** — enabled by default on all Neon databases

    ### Connection string format

    Neon provides two URLs per database: a pooled URL (via PgBouncer) for runtime queries, and a direct URL for migrations.

    ```
    # Pooled — use this for all application queries
    postgresql://USER:PASSWORD@ep-XXXXXX.us-east-2.aws.neon.tech/neondb?sslmode=require&pgbouncer=true

    # Direct — use this for migrations only
    postgresql://USER:PASSWORD@ep-XXXXXX.us-east-2.aws.neon.tech/neondb?sslmode=require
    ```

    ### Environment variables

    ```bash .env
    # Runtime queries (pooled via PgBouncer)
    DATABASE_URL="postgresql://USER:PASSWORD@ep-XXXXXX.us-east-2.aws.neon.tech/neondb?sslmode=require&pgbouncer=true"

    # Migrations only (direct connection — bypasses pooler)
    DIRECT_URL="postgresql://USER:PASSWORD@ep-XXXXXX.us-east-2.aws.neon.tech/neondb?sslmode=require"
    ```

    ### schema.prisma datasource

    ```prisma packages/db/prisma/schema.prisma
    datasource db {
      provider  = "postgresql"
      url       = env("DATABASE_URL")
      directUrl = env("DIRECT_URL")
    }
    ```

    ### Connection pooling with PgBouncer

    Neon's PgBouncer operates in **transaction mode** — a connection is held only for the duration of a single transaction, then returned to the pool. This supports thousands of concurrent application connections with a small number of actual PostgreSQL connections.

    <Warning>
    PgBouncer transaction mode does not support `SET` statements that persist across transactions (e.g. `SET LOCAL` for RLS). Nebutra's `withRls` sets the tenant variable inside a transaction, which is compatible with transaction-mode pooling.
    </Warning>

    ### Database branching for development

    Create a branch from the Neon console or CLI to get an isolated copy of your schema for a feature branch:

    ```bash
    # Neon CLI
    neon branches create --name feature/new-model --parent main
    ```

    Each branch has its own `DATABASE_URL`. Set it in your local `.env` or in Vercel's environment variable settings per branch.
  </Tab>
  <Tab title="Supabase">
    Supabase is a PostgreSQL platform with a managed dashboard, built-in auth, storage, and real-time subscriptions. Connection pooling is provided by Supavisor.

    ### Why Supabase

    - **Managed dashboard** — browse tables, run SQL, and view RLS policies in the Supabase Studio UI
    - **Supavisor** — session-mode pooling that supports `SET LOCAL` statements needed for RLS
    - **pgvector** — available as a first-class extension, enableable from the dashboard
    - **Storage** — S3-compatible object storage co-located with your database (used by `@nebutra/uploads`)

    ### Enabling pgvector

    Before running migrations, enable the pgvector extension from the Supabase dashboard:

    **Dashboard → Database → Extensions → Search "vector" → Enable**

    Or via SQL in the Supabase SQL editor:

    ```sql
    CREATE EXTENSION IF NOT EXISTS vector;
    ```

    ### Connection string format

    Supabase provides a pooled URL (Supavisor) and a direct URL per project:

    ```
    # Pooled via Supavisor (session mode — supports SET LOCAL)
    postgresql://postgres.PROJECTREF:PASSWORD@aws-0-us-east-1.pooler.supabase.com:5432/postgres

    # Direct connection (for migrations)
    postgresql://postgres:PASSWORD@db.PROJECTREF.supabase.co:5432/postgres
    ```

    ### Environment variables

    ```bash .env
    # Runtime queries (pooled via Supavisor)
    DATABASE_URL="postgresql://postgres.PROJECTREF:PASSWORD@aws-0-us-east-1.pooler.supabase.com:5432/postgres"

    # Migrations only (direct connection)
    DIRECT_URL="postgresql://postgres:PASSWORD@db.PROJECTREF.supabase.co:5432/postgres"
    ```

    ### schema.prisma datasource

    ```prisma packages/db/prisma/schema.prisma
    datasource db {
      provider  = "postgresql"
      url       = env("DATABASE_URL")
      directUrl = env("DIRECT_URL")
    }
    ```

    ### Connection pooling with Supavisor

    Supabase's Supavisor supports both **transaction mode** (port 6543) and **session mode** (port 5432). Use **session mode** (port 5432 in the pooled URL above) to ensure `SET LOCAL` statements for RLS work correctly.

    <Warning>
    If you use Supavisor in transaction mode (port 6543), `SET LOCAL` for RLS will not persist across statements in the same logical request. Always use session mode (port 5432) with Supabase when relying on `withRls`.
    </Warning>

    ### Running migrations with Supabase

    Migrations work exactly the same as with Neon:

    ```bash
    pnpm db:migrate
    ```

    Prisma uses `DIRECT_URL` for DDL statements and `DATABASE_URL` for all other queries.
  </Tab>
</Tabs>

## Choosing a provider

| Criteria | Neon | Supabase |
|----------|------|----------|
| Free tier | Generous (0.5 GB storage, 1 compute unit) | Generous (500 MB database, 2 GB bandwidth) |
| Branching | Yes — per-branch databases | No |
| Managed dashboard | Basic | Full-featured Studio UI |
| Connection pooling | PgBouncer (transaction mode) | Supavisor (session + transaction modes) |
| Built-in auth | No (use Clerk / Better Auth) | Yes (if desired) |
| Built-in storage | No (use `@nebutra/uploads`) | Yes (S3-compatible) |
| pgvector | Enabled by default | Available as extension |
| Auto-suspend | Yes (free tier) | Yes (paused projects) |

<Tip>
If your team relies heavily on per-PR database environments, choose Neon for its branching feature. If you want a single visual dashboard to inspect tables and run SQL without a separate tool, Supabase Studio is excellent.
</Tip>

## FAQ

<AccordionGroup>
  <Accordion title="Can I switch providers after going to production?">
    Yes. Because both providers are standard PostgreSQL, switching requires only a `pg_dump` / `pg_restore` of your data and updating the `DATABASE_URL` and `DIRECT_URL` environment variables. No application code changes are needed.
  </Accordion>
  <Accordion title="Why do I need two connection strings?">
    Connection poolers (PgBouncer, Supavisor) multiplex many application connections over a small pool of real PostgreSQL connections. They do not support DDL statements (like `CREATE TABLE` or `ALTER TABLE`) used during migrations. `DIRECT_URL` bypasses the pooler so Prisma can run migrations safely.
  </Accordion>
  <Accordion title="Is self-hosted PostgreSQL supported?">
    Yes, with additional setup. You need to ensure pgvector is installed, configure a connection pooler (PgBouncer is recommended), and provide a direct URL for migrations.

    **1. Install pgvector**

    ```bash
    # Ubuntu / Debian
    sudo apt install postgresql-16-pgvector

    # macOS (Homebrew)
    brew install pgvector

    # Enable the extension in your database
    psql -d your_db -c "CREATE EXTENSION IF NOT EXISTS vector;"
    ```

    **2. Install and configure PgBouncer**

    ```ini
    # /etc/pgbouncer/pgbouncer.ini
    [databases]
    nebutra = host=localhost port=5432 dbname=nebutra

    [pgbouncer]
    listen_addr = 127.0.0.1
    listen_port = 6432
    auth_type = scram-sha-256
    pool_mode = transaction       # required for Prisma
    max_client_conn = 500
    default_pool_size = 20
    server_reset_query = DISCARD ALL
    ```

    **3. Set environment variables**

    ```bash
    # Pooled connection (for app queries)
    DATABASE_URL="postgresql://user:pass@localhost:6432/nebutra?pgbouncer=true&connect_timeout=10"

    # Direct connection (for migrations — bypasses PgBouncer)
    DIRECT_URL="postgresql://user:pass@localhost:5432/nebutra"
    ```

    **4. Update `prisma/schema.prisma`**

    ```prisma
    datasource db {
      provider  = "postgresql"
      url       = env("DATABASE_URL")
      directUrl = env("DIRECT_URL")
    }
    ```
  </Accordion>
  <Accordion title="What about connection limits on the free tier?">
    Both Neon and Supabase free tiers have connection limits (typically 100–200 total connections). The pooler is essential on free tiers — never set `DATABASE_URL` to a direct connection string in a serverless deployment, as each function invocation would consume a connection.
  </Accordion>
</AccordionGroup>
