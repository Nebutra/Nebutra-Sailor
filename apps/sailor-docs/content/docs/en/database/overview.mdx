Nebutra-Sailor uses **Prisma** as the ORM and **PostgreSQL** as the database engine — one source,
generated, deployed first. See
[ADR 2026-09-25 database convergence](https://github.com/nebutra/nebutra-sailor/blob/main/docs/architecture/2026-09-25-database-convergence.md) for the full
decision; this page covers day-to-day use.

## Architecture

```
┌─────────────────────────────────────┐
│          Application Code           │
│  (Next.js Server Components, API)   │
└────────────────┬────────────────────┘
                 │ import { db } from "@nebutra/db"
┌────────────────▼────────────────────┐
│            Prisma Client            │
│     (type-safe query builder)       │
└────────────────┬────────────────────┘
                 │ PostgreSQL wire protocol
┌────────────────▼────────────────────┐
│         PostgreSQL Database         │
│  pgvector · generated RLS           │
└─────────────────────────────────────┘
```

`packages/platform/db/prisma/schema.prisma` is the **single source**: tables, and each table's
access rule as an `/// @rls` comment. Everything else — `generated/rls.sql`, the baseline
migration — is generated from it or re-applied to it on every deploy (`pnpm db:deploy`). There is
no scaffold-time database choice; `create-sailor` writes this schema every time.

## Schema layout

There are two Postgres schemas — see [Prisma Postgres Schemas](/architecture/multi-schema) for
why:

| PostgreSQL schema | Purpose |
|-------------------|---------|
| `public` | Every application table |
| `better_auth` | Tables Better Auth's own plugins (`organization`, `passkey`, …) manage |

This is not a "one schema per product domain" split — there is no `ecommerce`, `recsys`, or `web3`
schema, and no scaffold flag that would prune one.

## pgvector

PostgreSQL's `pgvector` extension powers AI embedding search (`@nebutra/search`, pgvector plus
full-text search — there is no separate search engine). Self-hosted PostgreSQL requires
`CREATE EXTENSION vector;` before running migrations; the `postgres:15-alpine`-based image
`create-sailor` wires up already has it.

## Command reference

| Command | When to use |
|---------|-------------|
| `pnpm db:deploy` | **The deploy command.** Runs pending migrations, then `platform.sql` + `generated/rls.sql`, then verifies. Exits non-zero on drift. |
| `pnpm db:check` | Read-only half of `db:deploy` — reports drift without applying anything |
| `pnpm db:generate` | After editing `schema.prisma` — regenerates the Prisma client and `generated/rls.sql` |
| `pnpm db:migrate` | Create and apply a new migration (local development) |
| `pnpm db:push` | Push schema changes without a migration file (local prototyping only) |
| `pnpm db:studio` | Open Prisma Studio |
| `pnpm db:seed` | Populate the database with development seed data |

<Warning>
Never run `pnpm db:push` against a production or staging database. It applies schema changes without a migration history, which can cause irreversible data loss. Production deploys use `pnpm db:deploy`.
</Warning>

## Multi-tenancy

A table's access rule is inferred from its `tenantId` / `organizationId` column (or declared
explicitly). Queries are scoped using PostgreSQL Row-Level Security (RLS) via the `withRls` helper
from `@nebutra/tenant`. See the [RLS guide](/database/rls) for details.
