Nebutra-Sailor's billing system is no longer a Stripe-only, single-file setup.
The current package is a **provider-aware billing core** centered on
`@nebutra/billing`.

## Current architecture

```text
apps/web billing surfaces
  └─▶ typed gateway calls
        └─▶ backends/gateway/src/routes/billing/*
              ├─▶ @nebutra/billing/checkout
              ├─▶ @nebutra/billing/subscriptions
              ├─▶ @nebutra/billing/credits
              ├─▶ @nebutra/billing/entitlements
              └─▶ @nebutra/billing/usage
```

Webhook handlers also live in the gateway under:

```text
backends/gateway/src/routes/webhooks/stripe.ts
```

## Package layout

The current billing package surface is split by concern:

| Area | Current location |
| --- | --- |
| Provider checkout orchestration | `packages/commerce/billing/src/checkout/` |
| Provider-specific Stripe helpers | `packages/commerce/billing/src/stripe/` |
| Subscriptions | `packages/commerce/billing/src/subscriptions/` |
| Credits | `packages/commerce/billing/src/credits/` |
| Usage / metering | `packages/commerce/billing/src/usage/` |
| Entitlements | `packages/commerce/billing/src/entitlements/` |
| Plan configuration | `packages/commerce/billing/src/config/` |

Earlier docs that pointed to `src/plans.ts`, `src/handlers/`, `src/portal.ts`,
or a monolithic `src/checkout.ts` are stale.

## Providers

The codebase currently contains provider modules for:

- Stripe
- Polar
- LemonSqueezy
- ChinaPay
- manual / credit purchase flows

The active provider choice depends on runtime configuration and the gateway
route invoking the checkout abstraction.

## Web app surfaces

The authenticated app already ships billing pages under:

```text
apps/web/src/app/[locale]/(app)/billing/
apps/web/src/components/billing/
```

Use those surfaces as the source of truth for product behavior before updating
documentation copy about plans, entitlements, or upgrade flows.

## Entitlements and usage

`@nebutra/billing` is responsible for more than checkout:

- feature entitlements
- credits
- usage metering
- overage calculations

That means a plan change can affect UI gating, API limits, and background usage
accounting, not just subscription state.

## Configuration guidance

Billing configuration now spans:

- provider credentials
- checkout readiness
- plan/limit configuration
- webhook secrets

Review the package entrypoints and your deployment environment together instead
of assuming a fixed pair of `STRIPE_*_PRICE_ID` variables is the whole story.
