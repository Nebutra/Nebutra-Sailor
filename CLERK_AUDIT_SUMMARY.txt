CRITICAL FINDINGS
================================================================================

1. CLERK TIGHT COUPLING
   - 31+ files in apps/web directly import @clerk/nextjs
   - API gateway uses @clerk/backend for JWT verification
   - No functional abstraction despite @nebutra/auth package existing
   - Hard to migrate to different auth provider without major refactoring

2. @NEBUTRA/AUTH PACKAGE STATUS
   - INCOMPLETE abstraction (Phase 1 only)
   - Clerk provider: Documentation bridge, not functional (returns null/throws)
   - Client hooks: Stubs only (no implementation)
   - Better Auth provider: WORKING (can verify as reference)
   - NextAuth provider: Stub (not implemented)
   - NOTE: Package has zero Clerk dependencies (design correct, but unused)

3. WEB APP ARCHITECTURE
   Root -> ClerkProvider -> NextIntlProvider -> DesignSystemProvider -> QueryProvider
   
   Auth data flow:
   proxy.ts (clerkMiddleware) 
     -> auth() to get session
     -> getToken() to get JWT
     -> API calls with Bearer token
     -> tenantContextMiddleware verifies token
     -> Database synced via Clerk webhooks

4. ENVIRONMENT REQUIREMENTS (Production)
   - NEXT_PUBLIC_CLERK_PUBLISHABLE_KEY (web app)
   - CLERK_SECRET_KEY (web app + api-gateway)
   - CLERK_WEBHOOK_SECRET (api-gateway)
   - CSP hardcoded for clerk.accounts.dev domains

5. CLERK-SPECIFIC FEATURES IN USE
   - Organizations (multi-tenant)
   - Roles (org:owner, org:admin, org:member, org:viewer)
   - Custom session claims (org_plan)
   - OAuth (Google + GitHub)
   - Email verification
   - Webhooks (via Svix)

================================================================================
COUPLING BY COMPONENT
================================================================================

MIDDLEWARE (proxy.ts)
  - clerkMiddleware() guards all requests
  - CSP hardcoded for Clerk domains
  - Fallback to noop proxy if no publishable key (dev mode only)
  - Refactor difficulty: HIGH (affects every request)

SESSION/USER RESOLUTION (lib/auth.ts)
  - auth() from @clerk/nextjs/server
  - currentUser() from @clerk/nextjs/server
  - Stores org_plan from sessionClaims
  - Refactor difficulty: MEDIUM (localized to lib/)

JWT EXTRACTION (lib/api.ts, lib/api/client.ts, hooks/use-api.ts)
  - auth().getToken() from @clerk/nextjs or @clerk/nextjs/server
  - Injected into API requests as Bearer token
  - Used by both server and client components
  - Refactor difficulty: MEDIUM (token generation only)

SIGN-IN/SIGN-UP (components/auth/)
  - useSignIn() hook with signIn.create(), signIn.password(), signIn.finalize()
  - useSignUp() hook with signUp.create(), signUp.password(), signUp.verifications.*()
  - Email verification via sendEmailCode()/verifyEmailCode()
  - SSO via .sso() method (oauth_google, oauth_github)
  - Refactor difficulty: HIGH (complex state machine)

UI COMPONENTS (multiple locations)
  - SignInButton, SignUpButton, UserButton (design-system-shell)
  - OrganizationList (select-org page)
  - All use Clerk appearance config
  - Refactor difficulty: LOW (can replace with custom components)

PERMISSIONS (hooks/usePermission.ts)
  - useOrganization() to get membership
  - membership.role mapped to internal role enum
  - Permission logic depends on Clerk org roles
  - Refactor difficulty: HIGH (auth claims tied to Clerk)

API GATEWAY (api-gateway/)
  - verifyToken() from @clerk/backend for JWT verification
  - Extracts userId (payload.sub), organizationId (payload.org_id), role (payload.org_role)
  - Webhook handler for Clerk events via Svix
  - Database synced: User, Organization, OrganizationMember
  - Role mapping: org:owner→OWNER, org:admin→ADMIN, org:member→MEMBER, org:viewer→VIEWER
  - Refactor difficulty: HIGH (on critical path for every API call)

ADMIN PAGES (app/(app)/admin/*)
  - clerkClient() backend SDK for listing users/organizations
  - Refactor difficulty: MEDIUM (backend only, not critical path)
